## 1. 美术风格定调

### 1.1 四方案对比与结论

**战斗资源包 < 2.5MB** 这一条就砍掉了大半选项：

| 维度 | 像素风 | 手绘序列帧 | **自研部件骨骼** | 商业骨骼（Spine） | 3D 渲成 2D |
|---|---|---|---|---|---|
| 单角色人日 | 10–15 | 80–120 | **25–35** | 25–30 | 45–55 |
| 2 角色包体 | ≈2.3MB（96px，760 帧） | ≈9.6MB（800 帧 × 12KB） | **≈1.0MB**（9 张 176px 部件图 + 2 个 JSON） | ≈0.5MB | 0.6–2MB |
| 改 3 帧硬直 | 重画 3 张 | 重画 + 重切图 | **改 3 组角度，2 分钟** | 改 3 个关键帧，5 分钟 | 改帧 + 重渲 |
| 亚像素位移 / 连续缩放 | 差 / 差 | 好 / 好 | **好 / 好** | 好 / 好 | 好 / 好 |
| 加角色、换肤 | 全套重画 | 全套重画 | **换部件 + 复用 rig 模板** | 换部件 + 复用骨架 | 换材质 |
| 技能门槛 | 像素动画师 | 原画 + 动画（贵、难招） | **会用 JSON 就行；AI 可直接出图** | Spine 动画师（市场有） | 3D 全流程 |
| 授权成本 | 免费 | 免费 | **免费** | Essential **$69** + 运行时商用授权 | 免费 |
| 一次性开发 | 0 | 0 | **+3～5 天（姿势编辑器）** | 0 | 管线 3–5 人日 |

**结论：自研部件骨骼 + 平涂赛璐璐**，纯数据驱动，运行时用 PixiJS 的 `Container` 层级变换，不引入任何第三方骨骼运行时。

- **为什么不选商业骨骼（Spine）**：能力上门槛最低、包体最小，但 **Trial 版不能保存工程也不能导出**，能用的是 Essential **$69/人**，且运行时 `@esotericsoftware/spine-pixi-v8` 的 license 是 `LicenseRef-LICENSE`（非 MIT，商用需随之授权）。v1 只需要"刚性部件绕 pivot 旋转"这一个能力——用不到 mesh、IK、deform、clipping，为它付钱并背一条授权，不划算（见 1.4）。
- **为什么自研反而更合适**：14 个部件各是一个 `Container`，`rotation` 直接由 `poses.json` 的角度驱动，`zIndex` 定层级。整个运行时不到 200 行，**没有任何二进制格式**，`poses.json` 可以用来 diff、可以手改、可以在 CI 里校验，美术调试成本比二进制 skeleton 低。14 个部件只对应 **9 张图**——四肢左右各共用一张（`arm_upper` / `arm_lower` / `thigh` / `shin` 靠 `flipX` 镜像），这是选它的另一个实惠：切图工作量几乎减半。
- **为什么不用序列帧**：除包体超预算近 4 倍，流程上是死结——M5 是帧数据调参期，起手/硬直/收招帧天天改，改一次就要重画，美术被迫在"逻辑没定稿"时反复返工。
- **不是像素风**（成本第二低，必须给理由）：① `cameraZoom` 在 0.95–1.35 逐帧插值，像素画在非整数缩放下必然锯齿；业界解法（Rivals of Aether）是 1:1 渲染 + 镜头吸附整像素，代价是全部美术按 3 倍网格作画、放弃连续缩放与 KO 特写，我们两样都要。② 击飞速度跨 1.5–75 像素/帧（`KB_MAX 2500 × KNOCKBACK_TO_SPEED 0.09`，v0.4.0 由 0.03 校准而来），每档都要单独做拖影序列。③ 每加角色要重画约 380 帧。
- **不是 3D 渲 2D**：需要"建模 + 绑定 + 动画 + 渲染管线"的复合技能，管线本身 3–5 人日，2 个角色摊不平；v2 角色到 6–8 个再评估。

### 1.2 风险对策与五条硬指标

部件骨骼的三个典型病：**补间塑料感**（只在关键姿势之间做 pose-to-pose，禁曲线平滑，每招 3–5 个关键姿势、中间不补超 4 帧）、**缺冲击力**（关键帧 3–5% 非等比缩放，拉长 8% / 压扁 5%，重击配独立 sprite 拖影，v1 不上 mesh）、**穿帮**（刚性部件在肩/肘/膝会露出接缝——对策是**每处关节做两层覆盖件**：大臂末端压住小臂根部 6px、大腿末端压住小腿根部 6px，接缝藏在覆盖件之下；外轮廓 3px、内部 1.5px，描边 `#0B0F16` 不用纯黑，关节上限肩 ±150° / 肘 ±140°，draw order 分层）。

五条硬指标写进美术规范：① **剪影测试**——纯黑填充缩到 88px 高，仅凭轮廓能分 idle / 出招 / 受击；M9 出拼图找 3 个没看过项目的人指认，错 1 个重画。② **三色原则**——每角色最多 3 个主色块（60/30/10），点缀色只在头部与武器末端。③ **阴影两阶**（固有色 −12% / −28%），不用渐变，720p 下会糊。④ **特效亮度上限**——单帧白场 ≤ 屏幕 25%、闪白 ≤ 3 帧，这既是观感也是光敏性癫痫的安全边界。⑤ **视觉总高约 88 逻辑像素**（720 的 12%）。注意区分两个高度：**碰撞体** `hurtboxH` 标准型 64 / 重型 74（见 [01 角色 §2.2](./01-characters.md)），**视觉总高**约 88 = 碰撞体 + 头顶发饰/举起的武器/3px 外描边，也就是"画出来比打得到的范围高一圈"，这是格斗游戏里正常的观感修正——因为场地宽 2400 而视口只有 1280，靠镜头拉近（zoom 1.35 时约 119px）与特效补存在感。

### 1.3 团队规模与并行排期

**美术不能等 M9**：M9 只有 4 天，做不出 2 角色约 70 招。最低配置 = 1 名 2D 美术（会切部件即可，不要求骨骼经验）+ 0.3 名特效，节奏是"设定先定、M6 出可动骨架、M7 末必须能出 idle/run/jump/attack/hit、M8–M9 边补招边对帧数"。M7 那个卡点没过就降级：色块角色 + 每角色只留 idle/attack/hit/ko 四套动画，保住"能打"，外观交 v0.3。

**自研方案把"动画师"的活变成了"调角度"的活**，这是它相对于 Spine 最实际的好处：一个招式的视觉就是 `poses.json` 里 3–5 组数字，谁都能改，改完存盘刷新就能看。M5 帧数据迭代期，这个速度差就是能不能按时完的区别。

### 1.4 为什么不用商业骨骼：Spine 的真实成本

| 项 | 事实 |
|---|---|
| Trial 版 | **不能保存工程、不能导出**——只能试用，不能产出任何可用素材 |
| Essential | **$69/人**（原价 $99）；可导出全部格式，但不含 Meshes / IK / Transform / Path / Physics constraint / Deformation / Weight / Clipping |
| Professional | $379（原价 $449），全功能 |
| 运行时授权 | `@esotericsoftware/spine-pixi-v8` 的 `license` 字段是 `LicenseRef-LICENSE`（**不是 MIT**），商用发布需与编辑器授权配套 |
| 结论 | v1 只需要刚性部件绕 pivot 旋转，Essential 的功能全用不上，**为它付 $69 + 一条授权链不值** |

同类的免费替代也都不成立：`pixi-dragonbones@5.7.0-1` 只支持 **PixiJS v4**（我们锁 8.x），且 2021 年后无更新；Rive 的定价是「free to build, paid plans to ship」，发布同样要钱。**自研是唯一既免费、又和 PixiJS 8 无版本绑定的路线。**

## 2. 分辨率与画面适配

### 2.1 设计分辨率：1280×720

与总纲附录 A 的 `VIEW_W 1280 / VIEW_H 720 / STAGE_W 2400` 对齐。改 1920×1080 要重标所有物理常数（×1.5 后 `GRAVITY 0.85`、`MAX_RUN 9.0`、`FULL_JUMP 12.5` 全部作废），像素量还翻 2.25 倍，8ms 渲染预算占用从约 30% 涨到约 62%。**逻辑分辨率锁死 1280×720，清晰度靠 `resolution` 提**——所有物理常数的可读性都建立在"1 单位 = 720p 下 1 像素"上。

### 2.2 Application 配置

```ts
// packages/client/src/game/render/createApp.ts
export const BASE_W = 1280, BASE_H = 720;

export function computeViewport(vw: number, vh: number, dpr: number) {
  const scale = Math.min(vw / BASE_W, vh / BASE_H);          // letterbox 缩放比
  return { cssW: Math.floor(BASE_W * scale), cssH: Math.floor(BASE_H * scale),
           resolution: Math.min(dpr * scale, 2.5) };
}

export async function createGameApp(m: ReturnType<typeof computeViewport>) {
  const app = new Application();
  await app.init({ width: BASE_W, height: BASE_H, resolution: m.resolution,
    autoDensity: false, antialias: false, background: 0x05060a,
    powerPreference: 'high-performance', preference: 'webgl',
    sharedTicker: false });                                  // 节奏归 FixedStepLoop 独占
  Object.assign(app.canvas.style, { width: `${m.cssW}px`, height: `${m.cssH}px` });
  return app;
}
```

| 配置 | 取值 | 为什么 |
|---|---|---|
| `resolution` | `min(dpr × scale, 2.5)` | 直接用 `devicePixelRatio` 会**欠采样**：1280 逻辑宽在 1920 CSS px 里拉 1.5 倍，dpr=2 时只有 1.33 设备像素/CSS 像素，画面发软 |
| `autoDensity` | `false` | 它把 canvas 的 CSS 尺寸锁成逻辑尺寸，固定视口 + letterbox 下没法按窗口缩放；只适合"铺满 + 扩展视野"，而该方案被 2.3 否决 |
| `antialias` / `sharedTicker` | `false` | 素材带 alpha 走线性过滤，MSAA 只对几何边缘有效（圆角/斜切都用 9-slice），开着多 8–15% 带宽；`sharedTicker` 会与 Vue 的 rAF 互相插队，某帧 step 两次或零次 |

### 2.3 适配策略：letterbox，不扩展视野

| 策略 | 做法 | 公平性 | 结论 |
|---|---|---|---|
| **letterbox** | 固定 16:9，四周黑边 | 所有玩家视野完全相同 | **采用** |
| 扩展视野 | 按窗口比例扩大可见世界 | 宽屏多看约 30% 水平世界 | 否决 |
| 拉伸 | 变形铺满 | 位置与判定错位 | 禁止 |

平台格斗**必须** letterbox：① **视口宽度 = 出界危险区的可见范围**，21:9 玩家能提前约 100ms 看到对手复归路线，3 命制里这是胜负级信息差；② **镜头缩放依赖视口宽度**（`zoom = VIEW_W / requiredWidth`），视口一变同一局镜头轨迹就不同，KO 特写构图与直播画面无法对齐；③ 1366×768 笔记本、2560×1440 显示器、带鱼屏必须是同一个画面。

三种典型窗口的换算结果：1366×768 → `scale 1.066`、渲染区 1365×768、几乎无黑边、dpr=2 时 `resolution 2.13`；1920×1080 → `scale 1.5`、满屏无黑边、`resolution 2.5`（被上限截断）；2560×1080（21:9）→ `scale 1.5`、渲染区 1920×1080、左右各 320px 黑边。黑边是 **CSS 背景**（`#05060a`），不画进 canvas——那是白烧填充率。高 DPI 三条规则：① **上限 2.5**（缓冲显存 = `1280×720×res²×4B`：res 2.5 → 23MB，3 → 33MB，4 → 59MB，超 25MB 就挤压图集与快照池）；② **只在需要时重建**——用 `matchMedia('(resolution: Xdppx)')` 的 `change`，不每帧轮询；窗口变化超 2px 才 resize（重建 framebuffer 要 3–8ms）；③ **文本一律 BitmapFont**（2× 预渲染），不用 `Text`——后者走 Canvas2D 生成纹理，`resolution` 一变就重建，伤害数字每秒变 3–5 次等于每秒上传多次纹理。

### 2.4 世界坐标 / 屏幕坐标 / 相机

坐标系同总纲：**y 轴向下为正**（与 Pixi 一致，省一次取反），地面 `y = 0`，跳起时 `vy < 0`。相机参数住在 `World` 里（`cameraX/cameraY/cameraZoom`），由 `battle-core` 每帧算：

```ts
// packages/battle-core/src/camera.ts —— 只写数值，不碰 Pixi（L1）
export function updateCamera(w: World): void {
  const [p0, p1] = w.fighters;
  const spread = Math.abs(p0.x - p1.x) + Math.abs(p0.y - p1.y) * 0.55;
  const target = clamp(VIEW_W / Math.max(SPREAD_MIN, spread + MARGIN_X * 2), ZOOM_MIN, ZOOM_MAX);
  w.cameraZoom += (target - w.cameraZoom) * 0.12;            // 系数写死 → 确定性
  w.cameraX += (clampAxis((p0.x + p1.x) / 2, w.cameraZoom, STAGE_W) - w.cameraX) * 0.18;
  w.cameraY += (clampAxis((p0.y + p1.y) / 2, w.cameraZoom, STAGE_H) - w.cameraY) * 0.10;
}
function clampAxis(v: number, zoom: number, size: number): number {
  const limit = Math.max(0, size / 2 - VIEW_W / zoom / 2);
  return clamp(v, -limit, limit);
}
```

只用 `Math.abs/max/min` 与四则（L2 允许），无三角函数、无随机——回滚重演的相机值完全一致，两台机器镜头一致，录像可复现。**相机只被渲染层读取，绝不反向影响物理**（L3）。换算只有两组式子（`render/Camera2D.ts`）：`screen = BASE_W/2 + (world − cameraX) × zoom`，反向 `world = (screen − BASE_W/2) / zoom + cameraX`。`screenToWorld` 不是摆设：调试层要用鼠标点选角色、KO 特写要用屏幕坐标放大字、屏外箭头要贴屏幕边缘摆。

**顶部倒计时在结束那一帧就停住**：读 `w.timeLeft`（模拟已冻结），不要读 `w.frame`。
结算页的「用时」读 `w.endFrame / 60`，同理 —— 否则胜利浮层上的计时会一直往上涨。

**屏外箭头的两档状态**（v0.10.2）：箭头本身表示「这个人在画面外」，颜色用槽位色（P1 蓝 / P2 橙）；当该角色**还有场外复归冲刺可用**时，箭头外面再加一圈青色环（`rgba(120,230,255,0.75)`，半径 17px）。两档状态的差别正是玩家最需要的那条信息：出画要不要紧，取决于还能不能救回来。

### 2.5 显示层结构：谁跟着相机动

```
app.stage
├─ backdropLayer   屏幕空间·最底·黑边内渐变底，不随相机
├─ worldRoot       世界空间·被 Camera2D 变换
│   ├─ stageFar / stageMid   视差 0.25 / 0.60（远景、中景）
│   ├─ platformLayer  1:1（必须与碰撞体严格对齐）
│   ├─ fighterLayer   1:1        ├─ fxLayer 1:1（火花/拖影，不做视差）
│   └─ debugLayer     仅 ?debug=1
├─ hudRoot         屏幕空间·不吃 zoom·只吃 15% 相机位移
└─ overlayRoot     屏幕空间·KO 大字/暗角/白闪，不随任何东西
```

- **`platformLayer` 绝不做视差**：玩家的边缘距离判断建立在"看到的平台 = 碰撞体"上，差 1 像素就抓边失误。
- **视差层要 clamp** 到 `[-farW + BASE_W, 0]`，否则镜头到边缘会露出图集外空白。
- **`hudRoot` 不吃 zoom、只吃 15% 位移**：数字在任何缩放下字号固定；完全不动又有"贴纸贴在屏幕上"的廉价感。

## 3. 页面结构完整清单

### 3.1 主流程与状态树

```
boot ─▶ login ─▶ menu ─▶ mode ─▶ char ─▶ stage ─▶ battle ─▶ result
                ▲                                            │
                └────────── ESC / 返回主菜单 ─────────────────┘

[boot] 预载 ui-core + 恢复会话（≤1.2s，超时按游客态进 menu）
  └─ 无会话 ─▶ [login] ─┬─ 游客一键进入（排位、排行榜不可用）
                        └─ 邮箱注册 / 登录 ─▶ [menu]

[menu] ─┬─▶ [mode] 单机 / 训练 ─────────────────────────────┐
        ├─▶ [lobby] 快速匹配 / 邀请码 ─▶ [room/:code] ───────┤
        ├─▶ [settings] ─ [profile]（需注册）─ [ranked]（需注册）
        ▼                                                   ▼
  [select/char]（v1 只 2 格可选）▶ [select/stage]（v1 仅 1 张）▶ [battle/:matchId]
                                                                  │
  ESC（单机/训练）─▶ 暂停浮层（同路由，不跳转）                      ▼
  [result/:matchId] ─┬ 再来一局 ▶ [select/char]
                     └ 返回 ▶ [menu]
```

|---|---|---|---|---|---|
| `/boot` | `Boot.vue` | 无 | 任意键跳过 | — | 唯一允许全局进度条 |
| `/login` `/upgrade` | `Login.vue` / `Upgrade.vue` | 无 / 需游客态 | ✔ 表单导航 | — | 原地升级保持 `user_id` |
| `/menu` `/mode` | `MainMenu.vue`※ / `ModeSelect.vue`※ | 需会话 | ✔ | — | 记住上次焦点 |
| `/lobby` `/room/:code` | `Lobby.vue` / `Room.vue`※ | 需会话 | ✔ 列表 | — | 队列、房间、邀请码 |
| `/select/char` `/select/stage` | `CharSelect.vue` / `StageSelect.vue`※ | 需会话 | ✔ 网格 | 预载缩略图 / 远景 | 单机·联机·训练三入口共用 |

### 3.3 游客 vs 注册用户

| 功能 | 游客 | 注册 | 实现 |
|---|---|---|---|
| 单机打 AI / 训练 / 休闲匹配 / 邀请码 | ✔ | ✔ | 不涉及排名，放行 |
| **排位 / 排行榜** | ✘ | ✔ | `requireRegistered` → `/upgrade` |
| 战绩 / 云设置 | 仅本地缓存 | 服务端记录 | localStorage vs `/api/profile/settings` |
| 昵称头像 / 结算页 CTA | 自动 `Guest-8F3A` / "注册以保存战绩" | 自定义（注册后改一次）/ "查看战绩" | 同组件按 `auth.isGuest` 分支 |

**注册墙只挡排位与排行榜，不挡游戏本体**：首局转化率比账号干净更重要；打 3 局、有了段位预期再引导升级，成功率远高于开机就要注册。

状态归属是硬边界：会话、设置、房间、队列、页面过渡进 Pinia（低频、要驱动 DOM）；`World`、输入缓冲、相机、特效队列留在 `GameRuntime` 的普通对象里（60Hz 热路径，**禁止进 Pinia**）；FPS/RTT/回滚次数放 `DebugStats` 普通对象、200ms 采样写 Pinia——这是唯一的"热路径 → 响应式"通道，且是抽样。任何 `reactive()` 对象都不能出现在 `step()` 调用链上：Proxy 每次属性读写多一层 trap，实测 4 角色 × 每帧 200 次访问 ≈ 0.6ms，直接吃掉 step 预算的 60%。

## 4. 每个页面的线框与交互

### 4.1 通用交互协议

**焦点环**不用 DOM `:focus`（手柄焦点与 DOM 焦点语义不同，Tab 会抢、会滚页面），自维护 `focusedId` + 二维网格寻路：候选节点投影到方向轴上，`score = 投影距离×2 + 垂直偏移×3`，取最小；找不到就停在原地。**不用"顺序循环"**：选人是 2×2 网格，按右从第 1 格到第 2 格后应停住而不是跳回第 1 格——循环会让玩家在锁定槽位上鬼打墙。

| 语义 | 键盘 | Xbox | PlayStation | Switch Pro |
|---|---|---|---|---|
| 方向 | ↑↓←→ / WASD | 十字键 / 左摇杆 | 同 | 同 |
| 确认 / 返回 | Enter / Space · ESC | A · B | ✕ · ○ | B · A |
| 页签 / 菜单 | Q / E · ESC | LB / RB · Start | L1 / R1 · Options | L / R · + |

Switch 的 A/B 与 Xbox 位置相反 → UI 提示一律用文字"确认 / 返回"，不画 `✕ ○`；只在设置页的"手柄诊断"里显示实时位图。**ESC 语义**：二级页面返回上一级；主菜单无动作（不退出浏览器）；战斗·单机开暂停浮层、战斗·联机开"认输确认"（不能暂停对手）；暂停浮层或模态框内只关浮层、不穿透；全屏下先退全屏，且 **100ms 内**不响应暂停。

加载态分四档：< 300ms 不显示（避免闪烁）；300ms–3s 用骨架屏且保留已有内容；> 3s 全屏进度 + 当前项名（"正在加载角色 aoi"）；401/5xx 走内联错误条 + 重试（保留表单）或 Toast + 跳登录（总纲 8.11 拦截器）；WebGL 不可用 / 资源 404 这类致命错误给全屏诊断（UA、分辨率、失败项）+ "低画质模式"重试。

## 5. 战斗 HUD 设计

### 5.1 结论：战斗内 HUD 全部用 Pixi 渲染

| 维度 | Vue 渲染 | Pixi 渲染 |
|---|---|---|
| 帧对齐 | 微任务批量 flush，与 rAF 不同步，最坏落后 1 帧 | 同一次 rAF 内绘制，零延迟 |
| 顿帧期间 | 世界冻结 6–10 帧而 HUD 还在动，一眼可见错位 | 可同时冻结 |
| 更新成本 | 6 个文本节点 × 60Hz ≈ 2.5–4ms（含 layout） | BitmapText 换 texture ≈ 0.15ms，且只在数值变化时换 |
| 可维护性 | 模板 + CSS 更舒服，但需两套时钟同步（CSS transform vs Pixi 相机） | 同一个变换树，但要手写布局 |

HUD 画在 Pixi 的 `hudRoot`（`render/HudView.ts`）：它每帧读模拟状态且必须与画面严格同帧，三条判据全部指向 Pixi。战斗页里 Vue 只保留三类浮层：**暂停按钮 / ESC 提示**（≤0.2Hz，不参与镜头变换）、**网络质量与重连遮罩**（1Hz 轮询）、**致命错误提示**（此时 Pixi 已不可用，只能用 DOM）。**为什么不用"Vue 渲染 HUD + CSS transform 跟相机"**：那要把 Pixi 相机状态每帧写回 Pinia 再让 Vue 消费，正是架构禁止的"响应式驱动 60Hz 数据流"；且 CSS 合成层与 WebGL 画布合成时机不同，撕屏比错位 1 帧更难看。

### 5.2 布局：大乱斗式「顶部计时 + 底部两角」

**v0.6.0 起战斗 HUD 精简为三个区**。旧版（v0.5.0）是「左上/右上各一块大面板 + 头像 72px +
段位条 88px」，占掉了屏幕上方近 1/4 的高度，而平台格斗最需要视野的恰恰是**上方的击飞弧线**——
角色被打飞时是往上走的，面板会盖住落点。所以改成大乱斗的布局：把一切压到屏幕边缘。

| 区 | 位置 | 内容 |
|---|---|---|
| 计时器 | 顶部正中 `(640, 14)`，`78×46` | 两位数秒，≤30s 转红并闪烁（`.urgent`） |
| P1 面板 | 左下 `left: 20, bottom: 18` | 头像 52×52（圆角 14、2px 玩家色描边）+ 名字 + 伤害数字 40px + 盾球 + 命数圆点 |
| P2 面板 | 右下 `right: 20, bottom: 18` | 同上镜像（只翻锚点不翻内容，否则数字反字） |
| 必杀冷却 | 底部正中一行三条 | `U` / `I` / `L` 各一条 4px 高细条，就绪时满格 brand 绿，冷却中按比例填充 |
| 操作提示 | 底部正中，`v-if="frame < 480"` | 8 秒后自动消失——新玩家需要，老玩家不该被永久占屏 |

**为什么伤害数字从 56px 降到 40px**：56px 是为"上方大面板"设计的，摆在下方两角时
56px 会和小头像不成比例、且离画面中心的战斗区太近。40px 在 1280 宽的视口里仍然
一眼可读（`≥150%` 时有红色脉冲与描边补强），但不再压住台面。

**为什么冷却条只有 4px 高**：冷却信息是"余光判断"的，玩家不需要读秒，只需要知道
"这条满了没"。4px 的细条在视野边缘足够分辨，又不会在底部形成视觉墙。
**必杀冷却不做成图标 + 数字**——那会让玩家停下来读，而格斗游戏里停下来读就是输。

**为什么操作提示 8 秒后消失**：`480` 帧 = 8 秒，足够打完开局第一波接触。
永久显示会盖住底部两角面板与场地边缘，而这正是复归时最需要看清的地方。

旧版的完整规格保留在 §5.2.1（变形盾球）与 §5.3（伤害数字配色）里，
那两套视觉规则没有变，只是尺寸与位置跟着新布局调整了。

锚点规则：**P1 子元素左对齐、P2 右对齐**，镜像只翻锚点不翻内容。命中抖动 ±2px、4 帧衰减，
相位用 `hash(frame, fighterId)` 算，**绝不能碰 `world.rngState`**（会推进模拟 PRNG，直接 desync）。

#### 5.2.0 盾球在战斗画面里也跟着角色画

除了 HUD 那颗缩略球，`drawFighter` 里还会在角色受击框中心画一颗**真实判定圆**——
两处尺寸必须同源，都从 `shieldRadius(f)` = `20 + ratio*14` 换算。
玩家在战斗画面上看到的那个圆，就是判定用的那个圆，**不是装饰**。

#### 5.2.1 变形盾：HUD 上的一颗球，不是一个条

盾在 HUD 上不是进度条，是**一颗大小随盾值实时缩放的圆球**，直径 8→28px（对应战斗里
判定半径 20→34）。它在战斗画面里也跟着角色画（画在角色受击框中心，是真实判定圆），
HUD 那颗是它的缩略对照——**两处尺寸必须同源**，都由 `shieldRadius(f)` 换算，否则玩家
会看着 HUD 觉得"还有盾"却被漏招打死。

| 盾值 | HUD 球径 | 球色 | 附加 |
|---|---|---|---|
| 100%–50% | 28 → 24px | 蓝 `#60A5FA` → `#3B82F6` 径向渐变 | 左上角高光让它是球不是圆 |
| 50%–25% | 24 → 18px | 蓝 → 青蓝 | — |
| <25% | 18 → 8px | 橙红 `#FF8A1F` → `#FF3B30` | `steps(2)` 硬闪，周期 480ms，**不用缓动**（要焦躁感） |
| 0（破盾） | 球消失 | — | 原地留 6 帧碎裂环 + HUD 位置改显"BREAK"12px 红字 150 帧 |

**缩放必须是 `linear` 过渡 90ms**（`transition: width 90ms linear`），不能用弹簧/缓动：
玩家要能从球的缩小速度预判"再挨一下会漏"，缓动会让这个反馈失真。
球不显示数字——盾值不是玩家该读的量，**球的大小才是**。

### 5.3 伤害数字

| 区间 | 颜色 | 描边 | 字号 | 附加 |
|---|---|---|---|---|
| 0–49.9% | `#F5F7FA` 白 | 3px `#0B0F16` | 56 | — |
| 50–99.9% | `#FFD84D` 黄 | 3px | 56 | — |
| 100–149.9% | `#FF8A1F` 橙 | 3px | 60 | 命中瞬间 scale 1.0→1.18→1.0，6 帧 |
| ≥150% | `#FF3B30` 红 | 3px + 8px 外发光 40% | 64 | 常驻脉冲 opacity 0.72↔1.0，周期 30 帧 |

**数值变化插 1 帧纯白**再回档位色：3 位数切换若没这一帧，玩家看不到"变了多少"。**右对齐 + 个位不动**，避免整块文字左右跳；取整显示（`Math.round`），上限 999，不显示小数。三层冗余（颜色 / 字号位数 / 命中弹跳）保证任一层失效都不影响判断。

### 5.4 命数 / 头像 / 段位与中央区域

- **命数图标**：3 个 20×20 剪影，剩余 = 玩家色实心，失去 = 空心 50% 透明；失去瞬间播 12 帧"碎裂"（6 块碎片）。剩 1 命时头像外圈 2px 脉冲环（周期 60 帧，与 ≥150% 脉冲错开相位）；头像 64×64 立绘裁切，受击边缘闪红 2 帧，KO 时整块去色为灰。
- **段位**：仅排位显示，5 格进度条 + 段位名；休闲与单机不显示，减噪也避免误以为掉分。
- **中央区域**：`mm:ss` 48px，≤10s 变红 + 每秒脉冲，最后 5 秒 tick 音效（View 侧）；`GAME 1/3` + `3 命` 两行 12px。`READY?` → `GO!` → `GAME!` 各 60 帧，由 `MatchPhase` 驱动，不额外维护计时器。
- **超时判定**：命数多者胜 → 相同则伤害低者胜 → 仍相同判平。v1 不做 sudden death（独立状态集合 + 独立 HUD，收益低于成本）。

### 5.5 特效层与事件消费

模拟层每帧往 `w.events` 推事件，`step()` 末尾清空。渲染层必须在**每次 step 后立即消费并拷贝**，且要应对回滚重放——重放会重新产出同一批事件，不去重会让特效翻倍：

```ts
// packages/client/src/game/render/FxLayer.ts
consume(w: Readonly<World>): void {
  for (const e of w.events) {
    const k = e.frame * 16 + e.seq;            // 回滚重放会再产出同一批事件 → 去重
    if (this.seen.has(k)) continue;
    this.seen.add(k);
    this.spawn(e);                             // 特效状态全在 View 侧，不写回 World
  }
  if (this.seen.size > 4096) for (const k of this.seen) if (k < (w.frame - 300) * 16) this.seen.delete(k);
}
```

**特效档位按击飞强度分四档**：`hit` KB < 300 → 小火花 + 头顶 1 帧白星（轻击音，短而干）；KB 300–800 → 中火花 + 顿帧 8 帧 + 3px 抖动（中击，带尾音）；KB 800–1200 → 大火花 + 屏幕边缘 20% 红晕 4 帧 + 6px 抖动（重击，低频冲击）；KB > 1200 → 全屏白 2 帧 + 拖影 + 10px 抖动（致命，长尾 + KO 音）。`ko` 冻结 90 帧 + `K.O.` 大字 + 镜头推近 + 慢镜；`ledge` 抓边尘土；`respawn` 复活台光柱 + 60 帧无敌闪烁；`shieldBreak` 蓝白爆闪（全屏白**最多 2 帧**）。

阈值是 M2 调的初值，放 `shared/constants.ts` 的 `FX_KB_TIERS` 便于连续调参。**KO 特写最容易违反 L5，必须写清**：逻辑层在出界那帧设 `phase = GAME_END_PAUSE`、`pauseFrames = 90`，后续 90 次 `step()` 只递减计数、其余逻辑全跳过、输入不采样——这 90 帧是**模拟状态**，进快照、会被回滚重演，两台机器完全一致。表现层的 `KoTimeline` 用毫秒时钟独立跑：0–120ms 白闪 → 120–600ms 大字弹入（scale 2.2→1.0）→ 600–1400ms 镜头推近 + 最近 12 帧位置的慢速回放（`prevX/prevY` 环缓冲）→ 1400ms 淡出。慢镜可以放表现层，因为世界已冻结、表现层时间不再需要与世界对齐，且它不写回模拟状态（L3）、不消费 sim 的 PRNG（L4）；镜头推近用 `applyZoom = w.cameraZoom * koBoost`，`koBoost` 是 View 侧 0–1 插值量，**不写回 `w.cameraZoom`**。

**连击计数**：受击者连续处于 hitstun 且未归零期间的命中累加（View 侧用 `hitstun` + `frame` 派生，不改逻辑），显示在**攻击者**面板下方 `×3 COMBO`、28px 强调色，最后一次命中后 60 帧开始 30 帧淡出——玩家看自己面板的频率远高于看对手的；回滚重放靠上面的去重键避免重复 +1。

### 5.6 数据流与性能

`battle-core` 的 `World` 只读地流向 `HudView.update(w)`、`FxLayer.consume(w.events)`、`AudioBus.consume(w.events)`，三者在每次 `step()` 之后跑。`HudView` **不持有 World 引用**，只在 `update(w)` 参数里接收，防止缓存上一帧的 World 被误用。更新频率：伤害数字仅命中时（3–5Hz，`Math.round(damage) !== lastDmg`）、计时 1Hz（`(frame/60)|0` 变化）、命数仅 KO 时、段位条静态。稳态每帧 4 次数字比较 + 0 次绘制，< 0.02ms。

### 5.7 战斗背景：四层视差与场地母题

背景不是"给平台垫个渐变"。它要同时做到三件事：让角色浮起来、让场地一眼可辨、让镜头移动时有纵深。

**四条硬规则（按优先级）**

1. **背景永远不许抢角色。** 所有层亮度压在 `--bg-2` 附近，靠"剪影 + 一点光"造纵深，不靠画得亮。角色是纯色块 + 3px 深描边，只要背景低亮度低饱和，角色自然浮起来。
2. **越远越亮、越近越暗。** 大气透视的反向用法：远处是雾（亮、低饱和），近处是逆光剪影（暗、近黑）。这样即使整层都暗，眼睛仍读得出前后。
3. **平台高度附近留一条空带。** 战斗发生在地面上下 200px 内，这一段必须是整屏最干净的地方，否则脚底轮廓和落地时机看不清。所以雾带压在平台**下方**。
4. **每张图的母题只做一件事。** 残灯台=一排灯笼，齿轮工坊=转动的齿轮，灰烬原=地平线上的火，天穹回廊=云层与浮岛。叠第三种元素就变噪点。

**四层视差系数**：`0.06 / 0.14 / 0.26 / 0.44`。数值刻意不成整数比——成比例时各层会同步到一个节奏，整体就像一块硬纸板平移。

**远景的垂直视差要按比例内插。** 远层的地面线是 `400 + (groundY - 400) * f`（`f` 为 0.5～0.55），不是直接用 `groundY`。直接给同一个 `groundY` 会让远近层同速，相机一上下跳整幅画就变成一张纸。

**地面线必须由相机算出来，不能写死。** 背景入口接收 `{ x, y, zoom, groundY }`，其中 `groundY = (0 - camY) * zoom + 400`，与平台绘制用的是同一个式子。写死 540 的话镜头拉远时背景的地平线会和平台错开——这类错误在静止画里完全看不出，一跑相机就露馅。

**平台材质跟着母题走。** 四组材质（木石 / 冷钢 / 焦岩 / 风化石）各有固定的三段渐变，组内共用数值；唯一随场地变的是顶面那道亮线，用 `accent`。这是"看起来是同一个世界"最省力的信号。

**预览与战场的分工。** 选场页的预览是**示意图**，不是缩小版战斗画面：同背景只借用 `accent` 做一团地面光 + 暗角，让人认出是同一张图；平台仍用示意色块，因为选场时看的是布局而非美术。

> 实现见 `packages/client/src/game/stageBackdrop.ts`（渲染层，允许用 `Math.sin`——铁律 L2 只约束模拟层）。
> `tools/check-backdrop.mjs` 用假 Canvas 记账跑四张场地 × 四组相机 × 三帧，
> 断言不抛异常、无 NaN 参数、上色指令数在区间内——它挡不住"不好看"，但挡得住"改个数字就白屏"。

### 6.1 设计 token

| token | 值 | 用途 | 对比度（对 `--bg-1`） |
|---|---|---|---|
| `--fg-0/1/2` | `#F5F7FA` / `#B6C2D4` / `#7A889E` | 主文字 / 次文字 / 禁用（仅 ≥18px） | 17:1 / 5.7:1 / 3.3:1 |
| `--bg-0` … `--bg-3` | `#05060A` / `#0F141D` / `#161D29` / `#222B3A` | 页面底与黑边 / 页面 / 卡片 / 悬停选中 | — |
| `--line` | `#2E3A4D` | 分割线、1px 边框 | — |
| `--brand` | `#A8E85C` | 强调、焦点环、主 CTA | 12:1 |
| `--p1` / `--p2` | `#3B82F6` 蓝 / `#F97316` 橙 | 玩家 1 / 玩家 2 | 5.0:1 / 6.6:1 |
| `--danger` / `--warn` | `#FF3B30` / `#FFB020` | KO、断线、≥150% / 高延迟、掉线倒计时 | 4.6:1 / 9.1:1 |
| `--success` / `--info` | `#34D399` / `#60A5FA` | READY、连接成功 / 链接、提示 | 8.7:1 / 6.2:1 |

**为什么玩家色是蓝 / 橙**：红绿色盲占男性约 6%，红/绿是最差的一对；蓝/橙在三种色觉缺陷下都保持 ≥3:1 色差。且红色必须留给"危险/KO"语义——若某玩家是红色，"他受伤了"与"这里危险"就撞色了。**为什么强调色是酸性黄绿**：不属于红绿易混对，与蓝、橙都拉开距离；深色底上 12:1，适合 2px 焦点环这种小面积元素。

### 6.2 字体策略

| 场景 | 方案 | 体积 | 理由 |
|---|---|---|---|
| 中文/英文 UI | 系统字体栈 | 0KB | 见下 |
| LOGO / 标题字 | SVG path（手绘 4–8 字） | ≈25KB | 矢量任意清晰，无字体授权问题 |
| 伤害数字 / 计时 / `K.O.` | BitmapFont 图集（16 字形） | ≈8KB | 必须绝对锐利，60Hz 下零成本换字 |
| 招式名字幕 | 系统栈 + `Text` 缓存 | 0KB | 只在受击瞬间出现，每秒重建 < 1 次 |

```css
font-family: -apple-system, "PingFang SC", "Microsoft YaHei UI", "Noto Sans SC", system-ui, sans-serif;
```

**为什么中文不用 Web Font**：① 3500 字子集 woff2 约 700KB–1.2MB，只取 800 字也要 200–300KB，而首屏 JS+CSS+UI 图集已占约 260KB（gzip），再塞字体就把 3s 逼到边缘；② **缺字比系统字体更丑**——招式名里的"霸/斩/裂"漏一个，同一标题出现两种字重，一眼廉价；③ PingFang 与微软雅黑本身是高质量黑体，自带中日韩混排与标点挤压。代价是不同 OS 字形宽度差 2–4%，所以**按钮宽度必须自适应**（`min-width` + padding），不能写死像素。

### 6.3 动效与组件状态

| 档位 | 用途 | 进入曲线 | 退出曲线 |
|---|---|---|---|
| 100ms | 悬停、按下、焦点环、开关 | `cubic-bezier(0.4, 0, 0.2, 1)` | 同 |
| 200ms | 面板展开、列表项、Toast | `cubic-bezier(0.16, 1, 0.3, 1)` | `cubic-bezier(0.4, 0, 1, 1)` |
| 300ms | 页面转场、模态、遮罩 | 同上 | 同上 |
| 战斗内 | **一律用帧数**：2/6/12/18/30/90 帧 = 33/100/200/300/500/1500ms | 线性 / 阶跃 | 同 |

**为什么战斗内禁止缓动曲线**：格斗手感来自帧数一致——第 6 帧出判定、第 9 帧收招。任何缓动都会让"看起来的时长"与"判定的时长"脱节，玩家学不会时机。缓动只存在于菜单。

| 组件 | 默认 | 悬停 | 按下 | 焦点 | 禁用 |
|---|---|---|---|---|---|
| 主按钮 | 底 `--brand`、字 `#0B0F16`、圆角 8 | 亮度 +8%、外发光 12px/20% | `translateY(1px)` + `scale(0.98)` 80ms | 2px `--fg-0` 环 + offset 2 | `opacity 0.4` + `not-allowed` |
| 次按钮 | 透明底、1px `--line` | 底 `--bg-3`、边框 `--brand` | 同上 | 同上 | 同上 |
| 列表项 / 卡片 | 透明底 / 底 `--bg-2` | 底 `--bg-2` + 左 4px 条 / 边框 `--brand` + `scale(1.03)` | `scale(0.995)` / `scale(0.97)` | 同上 + `scale(1.02)` / 3px 环 | 文字 `--fg-2` / 去色 + 锁图标 |
| 输入框 | 底 `--bg-0`、1px `--line` | 边框 `--fg-2` | 边框 `--brand` | 同按下 | 底 `--bg-1`、字 `--fg-2` |

焦点环永远 2px、`offset 2px`，加 1px `#05060A` 内阴影保证深浅底都可见；悬停与焦点**共用同一视觉状态**，避免双高亮；所有 `transition` 在 `prefers-reduced-motion: reduce` 下改为 `0.01ms`（见 10.2）。

## 6.5 角色本体：先用 SVG 路径（v0.10 现状）

> 本节讲**战斗中**的角色怎么画。菜单层的立绘/头像走位图，见 §6.6。

在真实的部件骨骼美术（`rig.json` + `poses.json` + 9 张部件图）到位之前，角色本体用**SVG 路径**画。这不是占位矩形，是可用级别的矢量剪影。

**为什么 SVG 路径能直接当贴图用**：Canvas 2D 的 `new Path2D(d)` 接受 SVG 的 `d` 字符串。等于零成本拿到矢量素材——不需要图集、不需要异步加载、不需要处理 DPR，而且随缩放不糊（角色在屏上只有 64–96 逻辑像素，位图缩放到 0.62 倍必糊）。

实现落在 `packages/client/src/game/charArt.ts`：

| 导出 | 作用 |
|---|---|
| `ART_UPPER` / `ART_LOWER` / `ART_FOOT` / `ART_FIST` | 肢体件，坐标约定「枢轴 (0,0)，沿 +x 到 1，厚度居中 y ∈ [-0.5, 0.5]」 |
| `HEAD_BASE` / `TORSO_BASE` | 头（圆颅收下颌）与对襟短打 |
| `CHAR_ART` | 四套角色配色 + 头饰 + 武器；`li` 布巾+斩骨刀、`aoi` 兜帽+提灯、`ken` 全盔+铁锤 |
| `drawLimb` / `drawPart` / `drawCrest` | 绘制函数 |

**描边不用 `stroke`**：非等比缩放下 `lineWidth` 会被拉成一边粗一边细。改用「先用墨色画一遍放大的同一形状（×1.16/×1.34 + 0.6），再用本色画正常大小」，得到等宽外轮廓，任何缩放都稳定。

**头饰是识别度的关键**：70 像素高的时候，玩家认不出服装细节，只能靠头饰与武器分辨角色——所以三个角色的头饰形状（横带+飘带 / 半圆罩 / 盔顶+面甲）刻意做得差异极大。

与 §7.4 的 `rig.json` 是同一套思路的两级：SVG 版本用固定枢轴与硬编码角度表，正式版换成 `poses.json` 驱动；`drawLimbs` 里 `seg(角度, 长度, 粗细)` 的接口与骨骼版的层级变换同构，替换时不影响调用方。

## 6.6 角色图片素材：从生成图到可用文件（v0.10.6 现状）

v0.10.6 起，角色的**菜单层**已经有真实美术（立绘、头像、道具贴图），但**战斗中的角色本体仍是 §6.5 的 SVG 路径**。这两层刻意分开：

| 层 | 用什么 | 为什么 |
|---|---|---|
| 选人预览 / 结算 / 个人主页 / HUD 头像 | webp 位图（立绘 456×768、头像 128×128） | 这些场景里角色是**静止且大**的，位图细节越多越好，也没有缩放抖动 |
| 战斗中的角色本体 | SVG 路径（`charArt.ts`） | 战斗中角色随相机在 0.62–1.15 倍之间连续缩放，位图必糊；且每帧 8 个肢体要独立旋转，位图无法拆分 |

### 6.6.1 素材管线

`tools/prepare-assets.py` 一条命令产出三类文件：

```
public/assets/characters/<id>/
  source/     原始生成图（jpg，不动，只在仓库里留档）
  reference/  整幅参考图，长边 <=1400，q=82   <- 给人看：动作参考、二次迭代
  portrait/   <id>_portrait.webp  <=512x768   <- 给 UI 用：选人、结算
              <id>_icon.webp      <=128x128   <- 给 UI 用：HUD、列表
  game/       prop_<name>.webp    <=192       <- 给战斗用：道具贴图
```

**裁切不写死坐标**。上一版是手写 8 组裁切框，实测 5 组切到了内容（右溢出最多 358px）。现在改成：先按 alpha 找内容包围盒，再留 4% 边距。坐标不再需要人工试，换一批图也不用改脚本。

**去背用「从四边连通填充」而不是抠白色**：把与画面边缘连通的背景像素抠成透明，角色身上被深色轮廓包住的白色高光不会被误伤。纯色背景的生成图用这个办法最稳，不需要 AI 抠图，也不需要人肉描边。

### 6.6.2 代码里的查表

两张表都在 `packages/client/src/game/portraits.ts`：

```ts
const ART: Record<string, CharArtSet> = {
  li: { portrait: '/assets/characters/li/portrait/li_portrait.webp',
        icon:     '/assets/characters/li/portrait/li_icon.webp',
        portraitFill: 1 },
}
const PROPS: Record<string, Partial<Record<string, string>>> = {
  li: { bottle: '/assets/characters/li/game/prop_bottle.webp' },
}
```

**为什么不写进 `CharDef`**：有没有美术是表现层的可用性问题，不该进 `rulesetHash`、也不该影响联机——同一个角色，A 有图 B 没图，照样能打。缺项即回落，绝不写空串。

**`portraitFill` 的坑**：这个字段表示「人物占画幅的比例」，用来放大裁掉留白。但 `prepare-assets.py` 已经按内容包围盒裁到贴边了，再设 0.62 会把头和脚一起切掉——所以**自动裁切之后这个值必须是 1**。只有拿到没裁过的原始构图时才需要调小。

### 6.6.3 组件与回落

`components/CharPortrait.vue` 是唯一入口：有图且未解锁 -> `<img>`，否则 -> `<CharSilhouette>`（几何剪影）。props 里的 `icon` 切 1:1 头像，`silhouetteOnly` 强制走剪影。

**刻意不做三态加载**（加载中 / 骨架屏 / 失败占位）：webp 单张 < 80KB、选人页同屏最多 4 张，闪一下不如直接显示剪影稳。`@error` 只做一件事——永久回落剪影，不重试 404。

### 6.6.4 战斗内道具贴图

`sprite(url)`（`game/sprites.ts`）是同步接口：返回 `Image` 表示已就绪，返回 `null` 表示还在加载、调用方照旧画几何图形。

**绝不能在 `draw()` 里同步创建 `Image` 并等它加载**：第一次画一定还没好，要么这帧空白（闪烁），要么卡住主线程。这里只在首次调用时发起加载，之后每帧查表。加载失败后永久返回 `null`，避免每帧重试一次 404。

## 7. 素材规范

### 7.1 图集划分：按"加载时机"分，不按"用途"分

| bundle | 内容 | 页尺寸 | 何时加载 |
|---|---|---|---|
| `ui-core` | 图标、9-slice、面板、段位徽章、LOGO | 1024² ×1 | 启动页 |
| `ui-battle` | HUD 专用：头像框、命数徽记、数字底衬、`K.O.` 大字 | 512² ×1 | 进战斗 |
| `char:aoi` / `char:ken` | 部件骨骼贴图 + 拖影 | 1024² / 1024²+512² | 选人确认后 |
| `fx-battle` | 火花、烟尘、白闪、拖影序列、命中环 | 1024² ×1 | 进战斗 |
| `stage:arena` | 远景/中景/平台三层 | 2048×1024 + 1024×512 ×2 | 进战斗（远景先到） |

**原则**：同一时刻需要的放一起，不同时刻的绝不合并。主菜单只要 `ui-core`；把 HUD 图标并进去，主菜单就要为 8 个图标多背 200KB。反过来角色图集绝不能和 UI 合并，否则"进战斗"变成"进主菜单"的成本。

### 7.2 命名规范

```
ui/icon_stock_20.png              UI 图标（含尺寸后缀）
ui/panel_result_9slice.png        九宫格面板
char/aoi/head_idle_01.png         角色部件：{部位}_{用途}_{序号}
fx/hit/spark_heavy_03.png         特效：{类别}/{种类}_{档位}_{序号}
stage/arena/bg_far.webp           场景：{stageId}/{层}
```

1. **全小写 + 下划线**，禁空格/中文/大写。Linux 服务器解包大小写敏感——"Mac 正常、上线 404"的经典事故就是 `Head.png` 与 `head.png`。
2. 序号两位补零（`_01`），保证文件管理器与构建脚本顺序稳定；目录用 `charId`（`aoi`）而非显示名，显示名会改，`charId` 是数据主键。
3. **部件名与状态机状态一一对应**（`attack_side_strong` ↔ `StateEnum.AttackSideStrong`），映射表放 `shared/anim.ts`，view 里禁止写字符串字面量。
4. 特效按**击飞档位**命名（`spark_heavy` 对应 KB > 800），不用"大/中/小"这类主观词。

### 7.3 导出格式与尺寸约束

| 内容 | 格式 | 参数 | 单文件 | 理由 |
|---|---|---|---|---|
| 角色部件贴图 | WebP 有损 | q=0.88，保 alpha | ≈190KB/角色 | 大面平涂 + 少量渐变，q88 暗部无色带；比 PNG 小 55–70% |
| 场景远景 / 平台 | WebP 有损 | q=0.82 无 alpha / q=0.92 保 alpha | ≈260KB / ≈90KB | 天空可更激进；硬边描边在 q<0.85 时边缘发毛 |
| UI 图标 / 9-slice | PNG-8（≤64 色） | 无损，外扩 2px | ≈6KB/张 | 1:1 显示，任何有损都在描边上出脏点 |
| 伤害数字 BitmapFont | PNG-24 | 无损 | ≈32KB | 文字必须绝对锐利 |
| 音效 / BGM | MP3 | 96kbps 单声道 / 128kbps 立体声 | ≈3KB/个 / ≈600KB/首 | 见下 |

- **音效用 MP3 不用 Ogg Vorbis**：Safari 不支持 Ogg Vorbis，选它就要维护两套编码 + 运行时探测；MP3/AAC 在所有目标浏览器可用，v1 不值得为省 15% 体积引入格式分支。
- **不用 AVIF**：编码慢（1024² 图集 3–8s），部分浏览器走软件解码，首帧 100ms+，直接吃掉"进战斗"的转场预算。**不用 JPEG**：没有 alpha，色块边缘振铃在放大后非常明显。

尺寸与打包四条硬约束：① **单张纹理上限 2048×2048**——部分 Android WebView 与老 iPad 上限 4096，且 4096² RGBA 就是 67MB 显存，250MB 预算不可接受；② 图集页以 **1024² 为主**（4MB 显存/页，6 页共 24MB），仅场景用 2048×1024；③ 角色部件按 **2×** 出图（屏幕 88px → 贴图 176px），4K 屏 `resolution` 到 2.5 时在 zoom 1.35 下仍清晰；④ 打包参数 `padding 2`、`extrude 1`、`powerOfTwo true`，**角色部件一律 `trim: false`**、UI 与 FX 才 `trim: true`。

**为什么 padding 2 + extrude 1**：线性过滤会采样相邻像素，部件间没有 2px 间隔时手臂边缘会渗进另一块的色边（"色渗"）；`extrude` 把边缘外扩 1px，配合 2px padding 才能彻底消除。**为什么角色部件必须 `trim: false`**：自研 rig 的 pivot 是**相对部件图打包后的矩形**定义的，trim 裁掉透明边就等于改了矩形原点，所有角度旋转都会围绕一个偏移点发生，表现为"手绕手腕外侧转"。UI 与 FX 不做层级变换，才能安全 trim。

**自研 rig 对图集布局有额外要求**：每个部件必须是**轴对齐的单张子图**，且**不允许旋转打包**（`rotation: false`）——旋转打包会让部件的局部坐标系倾斜，`rotation` 属性叠加后会绕错方向。同理**不允许九宫格拉伸**角色部件。

### 7.4 rig.json 与 poses.json：自研骨骼的两份数据

每个角色的美术后端就是两份 JSON + 一张部件图集，**没有任何二进制格式**。这是自研方案相对 Spine 最实在的一点：`git diff` 看得见，CI 能校验，出问题能手改。

#### rig.json——层级与挂点

```jsonc
// packages/client/public/char/aoi/rig.json
{
  "charId": "aoi",
  "atlas": "parts",                     // 部件图集 pack 名，见 parts.json
  "parts": [
    { "name": "hip",       "img": "hip",        "parent": null,       "pivot": [0, 0],    "z": 10 },
    { "name": "torso",     "img": "torso",      "parent": "hip",      "pivot": [0, -6],   "z": 11, "angle": -2 },
    { "name": "head",      "img": "head",       "parent": "torso",    "pivot": [0, -30],  "z": 13 },
    { "name": "armUpperR", "img": "arm_upper",  "parent": "torso",    "pivot": [7, -26],  "z": 12, "angle": 12 },
    { "name": "armLowerR", "img": "arm_lower",  "parent": "armUpperR","pivot": [0, 14],   "z": 12 },
    { "name": "armUpperL", "img": "arm_upper",  "parent": "torso",    "pivot": [-7, -26], "z": 9,  "angle": -12, "flipX": true },

    { "name": "footR",     "img": "foot",       "parent": "shinR",    "pivot": [0, 14],   "z": 10 },
    { "name": "thighL",    "img": "thigh",      "parent": "hip",      "pivot": [-5, 2],   "z": 8,  "flipX": true },
    { "name": "shinL",     "img": "shin",       "parent": "thighL",   "pivot": [0, 16],   "z": 8,  "flipX": true },
    { "name": "footL",     "img": "foot",       "parent": "shinL",    "pivot": [0, 14],   "z": 8,  "flipX": true },
    { "name": "weapon",    "img": "weapon",     "parent": "armLowerR","pivot": [2, 18],   "z": 14 }

```

**14 个部件、9 张图**：`hip` `torso` `head` `arm_upper` `arm_lower` `thigh` `shin` `foot` `weapon`。左右成对的四个（`arm_upper` / `arm_lower` / `thigh` / `shin`）再加 `foot`，靠 `flipX` 各复用一张。若角色没有武器（`weapon` 删掉且 `poses.json` 不写它），部件降到 13 个、图降到 8 张。

| 字段 | 含义 | 约束 |
|---|---|---|
| `name` | 部件唯一键，`poses.json` 里用它 | 驼峰，与 `shared/anim.ts` 的 `PART_KEYS` 常量一致 |
| `img` | 图集里的子图名 | 左右成对部件**共用同一张图**，靠 `flipX` 镜像 |
| `parent` | 父部件名，`null` 为根 | **必须无环**，CI 校验拓扑排序可完成 |
| `pivot` | 挂点在**父部件**局部坐标系中的位置（px，y 向上为负） | 决定旋转中心；肩在躯干顶端、肘在大臂末端 |
| `z` | 绘制层级 | 同一 `z` 按 `parts` 数组顺序；近侧肢体 > 躯干 > 远侧肢体 |
| `angle` | 静止角（度，顺时针为正） | 即 `poses.json` 缺省该部件时用的角度 |
| `flipX` | 水平镜像贴图 | **只翻贴图，不翻坐标系**——旋转方向对左右手保持一致 |

**`pivot` 是唯一容易搞错的地方**：它是"这个部件绕父级哪个点转"，不是"贴图自己的原点"。`armUpperR` 的 `pivot [7, -26]` 表示它挂在躯干局部坐标的右上方 7px、上 26px 处——也就是右肩。图集打包时部件图不需要在文件里对齐，位置全部由 `pivot` 决定。

#### poses.json——每个动画的关键姿势

```jsonc
// packages/client/public/char/aoi/poses.json
{
  "idle": [
    { "f": 1,  "torso": -2, "head": 0,  "armUpperR": 12, "armLowerR": 6,  "thighR": 0, "shinR": 0 },
    { "f": 13, "torso": -4, "head": 1,  "armUpperR": 14, "armLowerR": 8,  "thighR": 0, "shinR": 0 },
    { "f": 25, "torso": -2, "head": 0,  "armUpperR": 12, "armLowerR": 6,  "thighR": 0, "shinR": 0 }
  ],
  "attack_side": [
    { "f": 1,  "torso": -6, "armUpperR": 20,  "armLowerR": -10, "weapon": -20 },
    { "f": 6,  "torso": 14, "armUpperR": 96,  "armLowerR": -4,  "weapon": 10, "scaleX": 1.06, "scaleY": 0.96 },
    { "f": 9,  "torso": 10, "armUpperR": 88,  "armLowerR": -8,  "weapon": 6 },
    { "f": 22, "torso": 0,  "armUpperR": 30,  "armLowerR": -16, "weapon": -8 }
  ]
}
```

| 约束 | 说明 |
|---|---|
| **`f` 是逻辑帧号**（从 1 起），不是秒、不是归一化时间 | 与 `moveset.json` 的 `startup/active/recovery` 同一坐标系；美术把关键姿势从第 6 帧挪到第 8 帧，判定仍在第 6 帧出 |
| **首帧 `f` 必须为 1，末帧 `f` 必须等于该动画总帧数** | CI 断言；否则末段插值取不到右端点 |
| **单一动画的 `f` 严格递增** | CI 断言；重复帧号会导致插值除零 |
| **攻击动作的 `startup` 帧必须有一个关键姿势** | 否则视觉最高点出现在两个姿势之间，判定帧看起来"动作没到位"；这是 [01 角色 8.3](./01-characters.md) 那条规则在自研 rig 上的落地形式 |
| **循环动画首末姿势必须能接上** | `idle` 的首帧与末帧角度差 ≤ 2°，否则每循环一次抖一下 |
| **插值一律线性，禁缓动** | 缓动会让视觉峰值偏离 `startup` 帧；想要"前摇慢后摇快"就多插一个关键姿势 |
| 缺省的部件用 `rig.json` 的 `angle` | 姿势对象只写**变化的**部件，不要求全量 |
| 可选 `scaleX` / `scaleY` | 关键帧 3–5% 非等比缩放用于冲击力，见 1.2 |

#### 校验与工具

```bash
# CI 两条断言（tests/contract/rigSchema.test.ts）
# 1. rig.json：parent 无环、无悬空引用、pivot 是二元数数组、name 唯一
# 2. poses.json：每个 moveset 的 moveId 都有同名动画、f 严格递增、首帧=1、末帧=总帧数、
#    startup 帧有关键姿势、循环动画首末角度差 ≤ 2°
```

**姿势编辑器**（`packages/client/dev/pose-editor`，+3～5 天）：一个 Vue 页面，左边画布拖部件、右边滑杆调角度，按 `[` / `]` 切帧，`Ctrl+S` 直接写回 `poses.json`。它**不进生产包**，`pnpm dev:pose` 启动。功能清单收敛为五件事：拖拽调角度、切帧、复制上一帧、写入/读回 JSON、实时预览当前招式。不做曲线编辑（线性插值不需要）、不做 IK（v1 的刚性部件不需要）。


### 7.5 按需加载与体积预算

用 `Assets.loadBundle(name)` 分 bundle 加载，进度按**真实字节**而非资源个数推进——Pixi 的 `onProgress` 按个数算，会卡在 40% 再猛跳到 100%。做法是构建期生成 `alias → bytes` 表，每加载完一项累加并回调 `onBytes(done, total)`，进度条由此线性推进。

| 时点 | 加载内容 | 体积 | 观感 |
|---|---|---|---|
| 启动页 | 引擎 JS + `ui-core` | ≈110KB | 进度条 0→100%，1.2s 内完成 |
| 主菜单 idle | 2 张 128² 头像 | 24KB | 无感（`requestIdleCallback`） |
| 选人确认 | `char:{id}` + `stage:far` | ≈600KB | 正好被"选人→对战"转场遮住 |
| 进战斗 | `stage:mid/platform` + `fx-battle` + `ui-battle` + 常驻音效 | ≈900KB | 转场动画期间完成 |
| 战斗后台 / 结算后 | 对端角色骨骼 / 下一首 BGM | ≈380KB / ≈600KB | READY 期间 / idle |

各 bundle 目标/上限：`ui-core` 98/130KB（图集 + json + 字体）、`ui-battle` 60/90KB（HUD 图集）、`char:aoi` 232/300KB（图集 190 + 骨架 42）、`char:ken` 300/380KB、`stage:arena` 440/520KB（远景 260 + 中景 120 + 平台 60）、`fx-battle` 164/220KB、常驻音效 180/250KB（12 个短音效）。**战斗首帧合计 1.47MB / 2.5MB 硬上限**，余 1.0MB 给第 3、4 个角色。显存与内存（对 250MB 预算）：图集 6 页 28MB + 渲染缓冲（1280×720 @ res 2.5）23MB + 快照池 64KB + 音频解码缓存 18MB + JS 堆 60–90MB ≈ **160MB**，余量 90MB。

## 8. 从色块到成品的路线

### 8.1 M1–M8 全程色块，M9 才接美术

这不是"没钱做美术"的妥协，是**刻意的排期策略**：手感迭代速度取决于"改一帧能否立刻看到"，而美术的加载、打包、姿势对帧会把每次迭代从 30 秒拉到 5 分钟。

**M4 就用色块搭出 `rig.json` 的层级**是关键一步：14 个矩形按正确的父子关系和 pivot 挂好，跑起来就是个能摆姿势的火柴人。此后接真实部件图只是换 `img` 字段，**层级和角度数据一行都不用改**。这样 M4–M8 的手感调参与 M9 的接美术完全解耦。

| 阶段 | 角色表现 | 场地 / 特效 | 判定可视化 |
|---|---|---|---|
| M1 | 44×88 矩形（aoi）/ 46×92（ken） | 灰平台条 + 台壁 / 无 | hurtbox 绿框、平台线、着地标记 |
| M2 | + 速度矢量箭头（长 = \|v\|×4） | 同上 / 命中点小圆 | 击飞角度射线、KB 数值 |
| M3 | + 状态名（`IDLE`/`RUN`/`FALL`，头顶文字） | + 抓边点红圈（半径 = `GRAB_RADIUS`） | ledge 判定圈、无敌帧描边 |
| M4 | + 插值（60Hz → 平滑）+ **部件骨骼运行时**（`rig.json` 加载 + 角度插值，先用色块部件试跑） | 三层视差纯色块 / 火花（圆 + 缩放） | — |
| M5 | 两角色不同尺寸/颜色 + 招式名 | 同上 / 顿帧白闪、屏幕震动 | hitbox 红框（`?debug=1`） |
| M6 | + AI 标签（"思考 12 帧"） | 同上 / — | AI 目标点连线 |
| M7–M8 | 不变 | 不变 / — | 回滚次数、延迟叠加 |
| M9 | 部件骨骼（rig + poses） | 正式场景图 / 正式 FX | 关闭（保留 `?debug=1`） |

**M6 试玩评审必须用色块版本**：如果试玩者说"手感不对"，问题一定在物理/状态机而不在美术——这正是最便宜的返工时机。

### 8.2 占位渲染器：一个 `FighterView`，两条代码路径

```ts
// packages/client/src/game/render/FighterView.ts
export interface FighterSkin {
  readonly root: Container;
  /** 每渲染帧调用一次；p 是只读模拟状态，alpha 是插值系数 */
  sync(p: Readonly<FighterState>, alpha: number): void;
  destroy(): void;
}
export const createFighterSkin = (charId: number, textured: boolean): FighterSkin =>
  textured ? new RigFighterSkin(charId) : new BlockFighterSkin(charId);
```

**路径 A：色块**（M1–M8，同时是美术缺失时的回退）。构造时按 `CHAR_BLOCK[charId]` 画矩形（`roundRect` + 0.85 填充 + 白描边），再挂一个 11px 的 `BitmapText` 放头顶（`anchor(0.5, 1)`、`y = -h - 6`）。`sync()` 只做四件事：`root.x/y = lerp(prev, cur, alpha)`、`root.scale.x = p.facing`、受击时按 `hitlag` 奇偶闪白（`(p.hitlag >> 1) % 2`）、`DEBUG` 时把 `${STATE_NAME[p.state]} #${p.stateFrame}` 写进 label。`destroy()` 走 `root.destroy({ children: true })`。

**路径 B：部件骨骼**（M9）。构造时读 `rig.json` 建层级：每个部件是 `Container`（自身持有 `sprite`），`rig.json` 给出 `parent` / `pivot`（在父级坐标系里的挂点）/ `zIndex` / `defaultAngle`。`sync()` 里位置与朝向同路径 A，另加三步：

1. **取姿势对**：`const pa = POSES[animKey][i], pb = POSES[animKey][i + 1]`，其中 `i` 由 `stateFrame` 在本动画的姿势帧号数组里二分定位（姿势帧号即 `f` 字段，**就是逻辑帧号**）。
2. **插值角度**：`part.rotation = lerp(pa[partName] ?? rig.defaultAngle, pb[partName] ?? rig.defaultAngle, t) * DEG`，`t = (stateFrame - pa.f) / (pb.f - pa.f)`。**线性插值，禁缓动曲线**——缓动会让判定帧的视觉最高点偏离 `startup` 帧，手感立刻垮。
3. **朝向**：`root.scale.x = p.facing`，**不要对单个部件取反**（会让左右手臂互换，且描边在负缩放下会翻到背面）。

关键设计：`POSES` 里存的是**逻辑帧号**而不是时长（秒），所以美术把某个关键姿势从第 6 帧挪到第 8 帧，判定仍在第 6 帧出——**动画时长不参与任何计算**，和路径 A 的 `frames[]` 语义完全一致。

最后一帧的处理（避免"卡在待机第一帧"的错觉）：`stateFrame >= 最后一帧` 时用末姿势；循环类动画（idle/walk/run/fall/shield）把末姿势与首姿势之间也做插值，因此**循环动画的首末姿势必须能接上**（见 [01 角色 8.2](./01-characters.md)）。

```ts
// packages/client/src/game/render/RigFighterSkin.ts —— 核心约 60 行
const i = upperBound(POSES[key].map(p => p.f), p.stateFrame);
const pa = POSES[key][Math.max(0, i - 1)];
const pb = POSES[key][Math.min(POSES[key].length - 1, i)];
const t = pa === pb ? 0 : (p.stateFrame - pa.f) / (pb.f - pa.f);
for (const [name, part] of parts) {
  part.rotation = lerp(angleOf(pa, name), angleOf(pb, name), t) * Math.PI / 180;
  part.scale.set(lerp(scaleOf(pa, name, 1), scaleOf(pb, name, 1), t)); // 关键帧 3–5% 非等比缩放
}
root.x = lerp(prev.x, cur.x, alpha); root.y = lerp(prev.y, cur.y, alpha);
root.scale.x = p.facing;
```

#### 8.2.1 动画流畅性的三条硬规则

"动画卡"在原型阶段几乎总是下面三件事之一，与美术质量无关：

**规则一：动画相位必须来自模拟状态，不能来自渲染时钟。**

```ts
f.stateFramePhase++;   // 在 step() 里，随状态切换归零；进快照、进 checksum
```

不能用 `performance.now()` 或渲染帧计数器算相位。原因有两个：① 回滚重演时渲染时钟会
跳变，动画会抽搐；② 掉帧时渲染时钟 vs 模拟帧数不一致，跑动步频会飘。
`stateFramePhase` 进快照之后，回滚到第 N 帧重演，动画相位自动回到同一处——
**这不是为了好看，是为了正确**。

**规则二：所有视觉变换必须能由 `(state, stateFramePhase, 插值 alpha)` 纯推导。**

原型阶段的程序化动画（`BattleView.drawFighter`）就是这么写的：

| 效果 | 公式 | 为什么 |
|---|---|---|
| 跑动起伏 | `bob = sin(phase * 0.55) * 2.2` | 60Hz 下周期约 11.4 帧 ≈ 5.3Hz，接近真实跑频 |
| 出招前冲 | 三角包络 `t<0.45 ? t/0.45 : 1-(t-0.45)/0.55`，峰值 `lunge = 5` | **峰值必须落在判定帧**，否则"看着打到了却没判定" |
| squash & stretch | `jump → scaleY 1.08`、`land → 0.90` | 落地压缩 3 帧，是重量感的主要来源 |
| 受击抖动 | `shakeX = sin(phase * 2.4) * 3 * min(1, hitstun/12)` | 硬直越短抖得越弱，避免轻击晃得比重击还凶 |

这些量**一个都不写回 `FighterState`**。写回去就会进快照、参与 checksum，
变成联机 desync 的嫌疑对象——而且它们本来就是渲染侧概念。

**规则三：插值只用于位置，状态量取整帧。**

```ts
const ix = lerp(f.px, f.x, alpha);   // 位置用插值，消除 60Hz 的台阶感
const iy = lerp(f.py, f.y, alpha);
// 其余一律用当前帧的真实值：伤害、命数、盾值、state、attackFrame
```

不要把 `attackFrame`、`shield`、`damage` 也插值——那会让 HUD 数字在帧之间出现
"半格"，并且让"第 5 帧出判定"这种精确手感变得模糊。**位置是连续的，逻辑是离散的。**

#### 8.2.2 九方向肢体动画：角度表 + 包络

攻击的"方向感"全靠**手臂角度**表达。`drawLimbs` 就是一张 9×2 的角度表加一个三角包络：

```ts
// 每个方向一对角度：[蓄力角, 出招角]，单位度，0 = 水平朝前，正 = 朝上
const ARM = {
  neutral:       [ 24,    0],
  forward:       [-24,   42],   // 臂长 ×1.15，前伸的更远
  back:          [152,  104],
  up:            [ 62,   98],   // 臂长 ×1.1
  upForward:     [ 20,   52],
  upBack:        [128,  150],
  down:          [-30,  -72],
  downForward:   [  4,  -38],
  downBack:      [116, -168],   // 大幅回摆，视觉上真的"从身后抽回来"
}

const t   = f.attackFrame / totalFrames
const env = t < 0.4 ? t / 0.4 : Math.max(0, 1 - (t - 0.4) / 0.6)   // 三角包络
const deg = ARM[dir][0] + (ARM[dir][1] - ARM[dir][0]) * env
const ang = f.facing > 0 ? deg * DEG : Math.PI - deg * DEG
const ex  = Math.cos(ang) * len, ey = -Math.sin(ang) * len
```

三条必须遵守的细节：

- **包络峰值必须落在判定帧**（`t = 0.4`，对 5/4/9 的招式约在第 7 帧）。峰值早于判定 →
  玩家看到"手已经收回来了却打到了"；峰值晚于判定 → "打到的时候手还没伸出去"。
- **镜像用 `Math.PI - deg`，不是 `-deg`**。`-deg` 会让朝左时手臂从身体左侧穿过去
  （绕点旋转与镜像翻转不是一回事）。
- **出拳拖影必须画在 `g.scale(facing, 1)` 内部**，否则朝左出拳时拖影会画到身后。

腿部按状态取固定角度（`run` 摆腿 ±26°、`jump` 收腿屈膝、`crouch` 40/48、`knockdown` 摊平），
不参与攻击方向——**腿的语义是"在做什么动作"，手的语义是"打哪里"**，混在一起会两边都不清楚。

### 9.2 Vue 与 Pixi 的生命周期边界

```vue
<!-- packages/client/src/views/Battle.vue -->
<script setup lang="ts">
const host = ref<HTMLDivElement>();
let app: Application | null = null, runtime: GameRuntime | null = null;
const ac = new AbortController();

onMounted(async () => {
  app = await createGameApp(computeViewport(innerWidth, innerHeight, devicePixelRatio));
  host.value!.appendChild(app.canvas);
  runtime = new GameRuntime(app); runtime.start();      // 内部自管 rAF 的 FixedStepLoop
  app.canvas.addEventListener('webglcontextlost', onContextLost);
  window.addEventListener('resize', onResize, { signal: ac.signal });
});

onBeforeUnmount(() => {
  ac.abort();                                          // 一次性解绑全部监听
  app?.canvas.removeEventListener('webglcontextlost', onContextLost);
  runtime?.stop();                                     // 1. 先停 rAF，避免销毁中还在 draw
  runtime?.dispose();                                  // 2. 解绑输入、音频、事件
  app?.destroy({ removeView: true }, { children: true, texture: false, textureSource: false });
  app = null; runtime = null;
});
</script>
```

**为什么必须显式 `destroy()`**：WebGL2 context 有硬上限（Chrome 约 16 个），超了强制丢弃最老的，表现为"返回主菜单几次后战斗页黑屏"；GPU 纹理与帧缓冲不受 GC 管理，不 `dispose` 就只涨不跌；`ticker`/rAF 卸载后仍在跑，回调访问已销毁的 stage 会每帧报一条 `Cannot read properties of null`；`resize`/`keydown`/`visibilitychange` 监听累积后，第 5 次进战斗时一个按键会触发 5 次输入。

**为什么 `texture: false`**：纹理在 `Assets` 全局缓存里，销毁意味着下次进战斗要重新解码 1.5MB（约 200ms 卡顿）。策略是 `Application` 销毁但 `Assets` 缓存保留；切出战斗只 `Assets.unloadBundle('fx-battle')` 释放特效（最占地方且下次会重新生成），角色与场景图集常驻。

三个补丁：① HMR 幂等——`if (import.meta.hot) import.meta.hot.dispose(() => app?.destroy({ removeView: true }, { children: true }))`，否则热更新重复触发 `onMounted`；② 上下文丢失——`e.preventDefault()` + 暂停 + 提示 + 2s 后 `location.reload()`，比重建资源可靠；③ 窗口失焦——`document.hidden` 时暂停并改标题，回来单机弹暂停菜单（玩家可能已离开键盘）。

### 9.3 全屏、指针锁定与输入抽象

| 项 | 决策 | 理由 |
|---|---|---|
| 全屏 | 选人确认的点击里链式 `requestFullscreen()`，默认**开启**自动全屏 | 浏览器要求用户手势，借用"确认"这一下最自然；浏览器游戏最常见的抱怨是窗口太小看不清判定 |
| ESC 冲突 | 监听 `fullscreenchange`，用户按 ESC 退全屏时 **100ms 内**不再触发暂停 | 否则一次 ESC 同时退全屏 + 弹暂停，玩家会以为卡了 |
| 指针锁定 | **v1 不用** | 全程键鼠/手柄；Pointer Lock 隐藏光标并吞点击，暂停菜单、断线弹窗会点不动 |
| 鼠标 | canvas 上 `cursor: none`，移动 3px 后恢复；单击 = 单机暂停 | 双击会误触全屏，所以只认单击 |

```ts
// packages/client/src/game/input/types.ts
export interface BattleInputBits {
  left: boolean; right: boolean; up: boolean; down: boolean;
  attack: boolean; special: boolean; jump: boolean; grab: boolean;
  // 没有 shield 位：按下 down 即下蹲即防御（见 01 第 4.1 节）。
  // 少一个位不是省事——它直接从协议里删掉了"防御"这个独立动作的合法性，
  // 代码里想单独举盾都做不到，机制就不可能跑偏。
}
export interface InputSource {
  poll(): BattleInputBits;   // 逻辑帧开始时调用一次（60Hz），禁止在 rAF 里采样（L5）
  dispose(): void;
}
export class CompositeSource implements InputSource {          // 键盘手柄同时生效
  constructor(private readonly sources: InputSource[]) {}
  poll(): BattleInputBits { return this.sources.map(s => s.poll()).reduce(orBits); }
  dispose(): void { this.sources.forEach(s => s.dispose()); }
}
```

键盘与手柄都实现 `InputSource`，`CompositeSource` 按位或合并，`battle-core` 只认 `BattleInputBits`——加一个"手机虚拟摇杆"也只是再写一个实现。键位：移动 `↑↓←→`/WASD 或左摇杆·十字键；攻击 `J` / 跳 `K` / 必杀 `L` / 抓 `U`，手柄对应 `X` / `A` / `Y` / `R1`；**下方向键就是防御**，没有独立盾键。

手柄六个坑：① **每帧轮询** `navigator.getGamepads()`，不能缓存对象——浏览器会替换 `Gamepad` 实例，缓存的那个会变成永久冻结的快照；② `gamepadconnected` 只用来弹提示，不要在里面读按键；③ Chrome 要求**用户手势之后**才填充 `getGamepads()` 槽位，首次按键前查到的都是 `null`；④ 死区 0.35 过滤漂移、方向阈值 0.5 定判定点，两者必须不同；⑤ Switch Pro 的 A/B 与 Xbox 相反，默认按**物理位置**映射（下/右 = 确认），设置里提供"按标签映射"；⑥ 手柄断开直接毁掉一场比赛，`disconnected` 时立刻单机暂停 / 联机弹提示，不能静默继续。键盘侧：`keydown` 必须过滤 `e.repeat`（否则按住攻击连发）；方向是**持续状态**不是事件，要维护 `pressed` 集合，并在窗口失焦时清空（否则切回来会"卡住一直往右跑"）。

### 9.4 音效与音乐

四通道 `master/bgm/sfx/voice`，默认 80/55/85/70；总输出用 `(v/100)²` 曲线（人耳对数感知，线性滑杆要在中间位置听起来才"对半"）；战斗曲切换 300ms 交叉淡入；`voice` 只做 KO 与出场。

**为什么自写 AudioBus 而不引 Howler**：需求只有"3 条总线 + 音效池 + 一次 unlock + 顿帧时 −6dB"；Howler 的 30KB 与它自带的格式回退、空间音效都用不到，而真正的定制点（顿帧压低总线）在 Howler 里反而要绕。实现要点：`new AudioContext()` 后按 4 条 `GainNode` 串联；`play(name)` 用 `BufferSource` 播放并维护 `Map<name, count>`，同名并发上限 4（8 连击不会破音）；`duck(on)` 用 `setTargetAtTime` 在 60ms 内把 master 压到 0.5。

- **解锁**：第一次 `pointerdown`/`keydown` 里 `await ctx.resume()` 并播一个 0 音量的 1 帧 buffer——iOS 上只调 `resume()` 有时仍静音。
- **页面隐藏**：`visibilitychange` → `suspend()`，回来 `resume()`。**BGM 不做音高变化**（顿帧降 pitch 听起来廉价），只做 `duck`。

### 10.2 字号、对比与动效

- **UI 缩放**三档 100/115/130%，`html { font-size: calc(16px * var(--ui-scale)) }`；布局全用 flex/grid + `min-height`，禁固定高度，否则 130% 时文字溢出。
- **HUD 缩放**独立三档 90/100/115%，靠 `hudRoot.scale` + 重算锚点。**不能复用 UI 缩放**：320px 面板会被撑到 416px，HUD 是按像素锚死的。
- **对比度**：正文 ≥4.5:1、大字 ≥3:1；禁用态不用文字表达（改边框或图标）；`--fg-2` 只用于 ≥18px。
- **高对比 / 减少动效**：描边 2→4px、底衬 0.75→1.0；`prefers-reduced-motion` 下关镜头震动、关 KO 慢镜、白闪改边框脉冲，但**保留击飞拖影**（那是可读性信息，不是装饰）。

### 10.3 字幕与本地化

战斗内全部语音与系统提示都有字幕：`READY?` / `GO!` / `K.O.` / `TIME UP` / 胜负，中英双语。**屏外对手方向指示**（屏幕左右边缘 40px 三角 + 距离条）既是可玩性刚需，也是听障补偿——他们听不到"对手从左侧复归的风声"。音效可视化（v2）做命中时的边缘亮度脉冲；震动可关（`vibrationActuator`），语义与画面一致（重击才重震），不做"随机小震"。

| 文案类型 | 位置 | 例子 |
|---|---|---|
| UI 界面 | `locales/{zh-CN,en-US}.json`，key 形如 `page.section.element` | `menu.play.single` |
| 战斗内（Pixi） | 构建期由同一份 JSON 生成 `shared/i18n.ts` 常量 | `battle.ko` |
| 角色名 / 招式名 | 角色数据的 `name` 字段（随角色包下发） | `{ "zh-CN": "苍羽", "en-US": "Aoi" }` |

**建议：用 i18n key，不要直接写中文**，三条理由：① 硬编码后补英文等于全仓库搜索替换，漏一处就是"PLAY 单机战斗"的混排事故，且只有母语者能发现；② Naive UI 自带 locale 包（分页、空状态、日期选择器），`:locale` 一换组件内文案跟着变，硬编码会出现"组件英文 + 页面中文"的割裂；③ 角色与招式名是**数据**不是界面，随角色包分发与缓存，不能依赖前端构建产物。`pnpm i18n:check` 在 CI 跑三条：`zh-CN` 与 `en-US` 的叶子 key 集合必须相等；代码里 `t('...')` 的字面量 key 必须存在（AST 扫描，不用正则）；`en-US.json` 的**值**里不许出现中文（`[\u4e00-\u9fa5]`）——专治"复制粘贴忘了翻译"。数字与时间用 `Intl.NumberFormat` / `Intl.DateTimeFormat`，不手写 `%`、`:` 拼接（英文的百分比空格、日期月/日顺序都不同）。
