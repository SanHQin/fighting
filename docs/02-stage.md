## 1. 一张好场地由什么决定

传统 2D 格斗（拳皇式）的场地是一条平地加一张背景板：双方永远站在这条线上。平台格斗把地形变成规则的一部分——**被击飞后你必须自己走回来，而回来的路线由平台结构决定**。所以场地不是美术资源，是玩法的第三个参与者（另外两个是角色与招式）。

| 维度 | 传统 2D 格斗 | 本作（平台格斗） |
|---|---|---|
| 场地作用 | 背景，不参与胜负 | 垂直机动、复归路线、边缘攻防的载体 |
| 失败条件 | 血条清零 | 离开 blastZone |
| 相机 | 固定 / 简单平移 | 双人框选 + 动态缩放 |
| 对称性 | 无所谓 | 直接决定对局公平 |

### 1.1 公平性：四个可验收的硬指标

1. **左右镜像**：主台与副台关于 `x=0` 对称，误差 0px。不对称等于给某一侧玩家一个隐藏出生优势。
2. **可复归**：从 blastZone 四边的任意位置出发，都存在至少一条能回到台面的路线。验收方法：把角色放到「blast 边缘向内 20px、速度朝场内」，240 帧内必须能站上台面。
3. **无死角**：不存在「被击飞到这里必死」的角落（深井、平台夹缝、台壁与副台形成的口袋）。
4. **无单向优势台**：不存在只有一侧能站上去、或只有一侧会被卡住的台面。

### 1.2 多样性：层次与边距的取舍

垂直层次上限 3 层（主台 + 侧台 + 高台）。层次再多，复归路径的读图成本超过收益，且回滚快照的碰撞开销线性上升。水平方向只靠**出界边距**制造张力：边距越窄，一次命中就能终结，翻盘困难；边距越宽，edge-guarding 的时间越长，观赏性上升但节奏拖沓。

### 1.3 三条设计原则

| 原则 | 数值化（本作常量） | 后果 |
|---|---|---|
| **主平台宽度决定交战空间** | 1500px ≈ 1.17 屏（视口 1280）；MAX_RUN=9 跑穿 167 帧（2.78s） | 太窄：一被击飞就出界；太宽：变成追逐赛 |
| **副平台决定垂直机动路线** | 层高 75px = 全跳 86px 的 87%，单跳可达、余量 11px | 跳得上去但要走位；再高就得二段跳，机动成本变高 |
| **出界边距决定翻盘难度** | 台沿到 blast 水平 370px ≈ 41 帧横移 | 够一次空中干扰 + 一次抓边；再宽守尸就太安全 |

这里每个数都能被常量反推（推导见 §8.2）。**改一个数就要重算一次**，不要凭手感调——手感调的是击飞衰减，不是地形。

## 2. 场地数据结构

### 2.1 类型定义

```ts
/** 场地是只读数据：加载后冻结，不参与模拟写入，可哈希。 */
export interface StageDef {
  id: string;
  displayName: string;
  version: number;              // 数据版本，加载期迁移用，不参与模拟
  blurb: string;                // 一句话介绍，选人/选台界面显示
  danger: 1 | 2 | 3 | 4;        // 危险等级，UI 用四档 chip
  platforms: Platform[];
  blastZone: Rect;
  cameraBounds?: Rect;          // 可选：不给就用 blastZone 内缩
  spawnPoints: Vec2[];
  hazards: HazardDef[];         // ★ 场地事件（地火/齿轮/风/熔岩/落石）
  bgTop: string; bgBottom: string; accent: string;
}

export interface Platform {
  id: number;
  type: 'solid' | 'passthrough' | 'ceiling';
  shape: 'rect' | 'polyline';   // 只支持矩形与折线，不支持曲线
  x?: number; y?: number; w?: number; h?: number;
  points?: Vec2[];
  thickness?: number;
  grabbable: boolean;
  // ★ 可破坏：给了 hp 就会被伤害打碎，respawn 帧后自动重建
  hp?: number;
  respawn?: number;
  // ★ 移动：水平三角波往返
  moveAmp?: number;
  movePeriod?: number;
  movePhase?: number;
}

/** 场地事件：只描述"什么时候、在哪个矩形里、造成什么"，运行时不改它 */
export interface HazardDef {
  kind: 'flame' | 'gear' | 'wind' | 'lava' | 'rock';
  period: number;       // 一个完整周期的帧数
  phase: number;        // 相位偏移，用来错开多个同类事件
  duration: number;     // 单次激活持续的帧数
  damage: number;       // 0 表示只推不伤（如上升气流）
  angle: number;        // 击飞角度
  baseKB: number;
  x: number; y: number; w: number; h: number;   // 触发区
  label: string;        // 中文名，进 UI
}

export interface Rect { x: number; y: number; w: number; h: number }
export interface Vec2 { x: number; y: number }
```

**`hazards` 与 `plats` 的分工**：`StageDef.hazards` 是**只读定义**（周期、相位、伤害），
`World.hazards` 是运行时状态（当前是否激活、冷却）。物理只读运行时那份。
这跟 §平台 里 `stage.platforms` vs `World.plats` 是同一条原则——定义与实例分开，
否则联机两边看到的事件相位会对不上。

三张「危险」场地的差异全在这三个字段的组合上：

| 场地 | `danger` | 可破坏平台 | 移动平台 | `hazards` |
|---|---|---|---|---|
| 残灯台 | 1 | 2（hp 46 / 420f） | 0 | 无 |
| 齿轮工坊 | 2 | 2（hp 38 / 360f） | 1（`moveAmp 130` / `movePeriod 300`） | 2 × `gear`（12%，period 240，phase 0/120） |
| 灰烬原 | 3 | 2（hp 30 / 300f） | 0 | 3 × `flame`（9%，period 300，phase 0/100/200，duration 80）+ 1 × `lava`（14%，period 900，duration 220） |
| 天穹回廊 | 2 | 2 条 `solid` 窄桥（hp 52 / 480f） | 1 | 1 × `wind`（0 伤害，托人）+ 2 × `rock`（11%，period 220） |

五条约定，写进 loader 的校验里：

- **原点**在主平台地面中心，`y` 向下为正（屏幕坐标）。所以 `-75` 就是「台面上方 75px」，JSON 可读性最好。
- `rect` 的 `y` 是**顶面**而不是中心。碰撞只关心顶面与左右面，写中心每帧多两次加减，且容易和 `thickness` 混淆。
- **台壁不单独建条目**：主平台是 `solid`，它的左右侧面就是台壁。重复建模会让角色在扫掠时被两套面夹住。
- `id` 从 0 连续递增，它同时是 `FighterState.platformId` 与快照里的数组下标。
- 派生数据在加载期算好、不存 JSON：`ledges: Ledge[]`（每个 `grabbable` 平台的左右两个边缘点及朝向）、`aabbs: Rect[]`（`polyline` 离散后的台阶）。

### 2.2 片段示例

```ts
const sample: Platform[] = [
  // rect：x/y 是左上角，y 是顶面；单向台用 12px 薄板
  { id: 1, type: 'passthrough', shape: 'rect', x: -655, y: -75, w: 320, h: 12,
    thickness: 12, grabbable: false },

  // polyline：points 必须按 x 升序，y 是该点的顶面高度（v1 数据里不使用）
  { id: 9, type: 'solid', shape: 'polyline',
    points: [{ x: -200, y: 0 }, { x: 0, y: -40 }, { x: 200, y: 0 }],
    grabbable: false },
];
```

### 2.3 为什么形状只有 rect 和 polyline

| 形状 | 碰撞算法 | 确定性 | 实现成本 |
|---|---|---|---|
| `rect` | AABB 扫掠，`maxStep=4` 分步，闭式比较 | 完全确定 | 已实现（见 [战斗系统](./03-combat-system.md) 第 4.5 节） |
| `polyline` | 加载期离散成 8px×2px 台阶，运行时仍走 AABB | 完全确定 | +40 行 |
| 贝塞尔 / 圆弧 | 每帧求最近点或交点，只能数值迭代 | **不可靠** | 200+ 行且调不完 |

两个理由，都足以否决曲线：

1. **L2 层禁止三角函数**。圆弧的参数方程 `x = cx + r*cos(t)` 直接写不出来；就算用查表，碰撞也退化成「数值解一个含三角函数的方程」。
2. **迭代次数不可控**。解方程只能迭代，终止条件一旦依赖浮点误差，两台机器就可能在某一帧得到不同的交点 → desync。而 AABB 的扫掠是纯比较运算，有闭式解、无迭代、无浮点累计误差。

### 2.4 polyline 在 v1 只做校验和渲染

```ts
const STAIR_RUN = 8;    // 每级台阶 8px 宽
const STAIR_RISE = 2;   // 每级台阶 2px 高
const MAX_SLOPE = 45;   // 超过 45° 的段直接按墙处理
```

- 台阶化必然带来 1–2px 的顿挫（`tryMoveX` 会被每一级立面挡住一帧）。所以 **v1 场地不含斜坡**，`polyline` 只走数据校验与渲染。
- 若 v2 真需要顺滑斜坡，正确做法是加 `slopeMove()`（沿斜面方向的投影位移，约 60 行），而不是把台阶加密到 1px——那只是把顿挫变小，成本却线性上涨。

## 3. 平台类型详解

### 3.1 碰撞矩阵

| 方向 \ 类型 | `solid` | `passthrough` | `ceiling` |
|---|---|---|---|
| 从上落下 | 挡住并站立 | 挡住并站立（条件见 3.3） | 不挡 |
| 从下上升 | 挡住（顶头，`vy=0`） | 穿过 | 挡住（顶头） |
| 左右平移 | 挡住（`vx=0`） | 不挡 | 不挡 |
| 可作为站立面 | 是 | 是 | 否 |
| 可抓边 | 仅 `grabbable=true` | 否（薄板没有可抓的边缘） | 否 |

### 3.2 单向平台的视觉表达

玩家必须先「知道」这块板可以穿过去，才可能去用它。六个线索按优先级：

| 线索 | 做法 | 目的 |
|---|---|---|
| 厚度 | 12px 薄板（实心主台 100px） | 一眼分辨「薄板 = 可穿」 |
| 顶面高光 | 顶部 2px 亮线，比台面亮 15% | 强调「只有上面能站」 |
| 底部 | 50% 透明、无描边 | 暗示下方没有实体 |
| **站立时顶面呼吸** | 顶面高光在角色站上去后按 `sin` 做 0.6→1.0 的 90 帧循环 | 暗示「这块板对你是活的」 |
| 穿过瞬间 | 台面 alpha 0.5 → 0.3，持续 14 帧后恢复（对齐 `DROP_THROUGH_FRAMES`） | 给出「你刚穿过去了」的即时反馈 |
| 站立时 | 脚下 24px 宽的椭圆接触阴影 | 告诉玩家当前踩在哪块板上 |

**穿台的视觉提前量**：玩家按下 `蹲+跳` 的那一帧，台面立刻开始变透明，不等真正穿过。
这 4 帧 `jumpSquat` 的提前反馈是"我能穿"这一认知的唯一教学途径——
玩家的第一次穿台大概率是试出来的，不是读说明书读来的。

渲染顺序：角色在台面上方时台面后绘、在下方时台面前绘，避免「人卡在板子里」。**不要**用虚线边框——1080p 下会闪烁，且让整个画面显得廉价。

### 3.3 穿越规则（与 [03 第 4.5 节](./03-combat-system.md) 的 `canLandOn` 一致）

```ts
function canLandOn(p: Platform, f: FighterState, sy: number, dropTimer: number): boolean {
  if (p.type !== 'passthrough') return true;
  if (dropTimer > 0) return false;                    // 刚蹲跳穿下来：14 帧内不被同一块接住
  if (sy <= 0) return false;                          // 上升/平飞：穿过
  if (f.prevY + HURTBOX_BOTTOM > p.y) return false;   // 上一帧已在平台下方：穿过
  return true;
}
```

| 情形 | `sy` | 上一帧脚底 | 蹲+跳 | 结果 |
|---|---|---|---|---|
| 从下往上穿 | ≤ 0 | 任意 | 任意 | 穿过 |
| 上升后从板内侧下落 | > 0 | 在板下方 | 任意 | 穿过 |
| **站在板上蹲着按跳** | — | 在上方 | 是 | **下穿（主动）** |
| 站在板上只按住下 | > 0 | 在上方 | 否 | **站着不动（防住）** |
| 正常下落 | > 0 | 在上方 | 否 | 站上去 |

**关键变化（v0.5.0）：穿下平台是「蹲 + 跳」，不是「按住下就掉」。**
原因是下方向键已经绑给了防御——如果按住下同时又是"掉下去"，每一蹲防都会误掉台。
现在穿台是一个明确的动作（`jumpSquat` 4 帧前摇），对手能看见并惩罚，掉平台是**风险**不是
顺手福利。实心台（`solid`）上蹲跳只是普通跳，判定只对 `passthrough` 生效。

两条补充，缺一就会出 bug：

- **`DROP_THROUGH_FRAMES = 14` 帧免接住**：穿下去之后 14 帧内不被**同一块**平台重新接住。
  8 帧不够——本作下落初速低（`vy=1` 起跳、重力 0.85），8 帧只掉 33px，还在 12px 厚板的
  判定带里；14 帧掉到约 90px，稳定出板。落到下层平台时正常接住，不受此窗口影响。
- **不要新增状态位**：穿台靠 `dropThroughTimer` 这一个计时器表达，不引入 `IsDropping` 状态
  （多一个状态就多一条转移边，见 L7）。蹲跳同帧把 `vy` 设成正值并清 `onGround` 即可。`

### 3.4 `ceiling` 的用途

v1 不使用。v2 的室内场地（灯塔塔身内部、洞穴）用它压缩垂直机动：跳跃会撞头，二段跳不再是万能解。注意 `ceiling` **不提供站立面**，不要拿它拼「限高走廊」的地板。

### 3.5 可破坏平台

给了 `hp` 的平台会被**伤害**打碎。碎掉之后 `broken = true`，物理跳过它，`respawn` 帧后自动重建。

```ts
export function damagePlatform(w: World, p: PlatState, dmg: number) {
  if (p.broken || p.maxHp <= 0) return
  p.hp -= dmg * C.PLATFORM_HP_SCALE
  p.flash = 8                       // 只影响渲染，不进校验和
  if (p.hp <= 0) {
    p.broken = true
    p.hp = 0
    p.respawnTimer = p.respawn
    w.events.push({ type: 'platformbreak', who: 0, x: p.x + p.w / 2, y: p.y })
  }
}
```

| 场地 | 平台 | `hp` | `respawn` | 打碎需要 |
|---|---|---|---|---|
| 残灯台 | 两侧单向台 | 46 | 420 帧（7 秒） | 约 3 次重击 |
| 齿轮工坊 | 两侧单向台 | 38 | 360 帧（6 秒） | 约 2–3 次 |
| 灰烬原 | 两侧单向台 | 30 | 300 帧（5 秒） | 约 2 次 |
| 天穹回廊 | 两条窄桥（`solid`） | 52 | 480 帧（8 秒） | 约 3–4 次 |

**`hp` 只减不因为对手重量缩放**：平台耐久是一个"场地属性"，让重角色更容易砸碎平台
会变成隐藏的平衡变量，玩家无法从 UI 上得知。宁可所有人都一样。

**`flash` 不进校验和**：它是纯视觉的受击闪白计时，写进 `World` 但**不参与 `checksum`**
（同相机震动，见 §7.6）。这是"进快照但不进校验和"的第三类字段——
它不影响任何判定，只影响像素，如果进了校验和，两边闪白帧数差 1 帧就会误报 desync。

**重生时的位置要还原到 `baseX/baseY`**，不能保留移动平台的当前偏移，
否则"平台碎了 → 重生"会发生在半路上。

### 3.6 移动平台

`moveAmp > 0` 的平台按三角波水平往返：

```ts
export function updateMovingPlatforms(w: World) {
  for (const p of w.plats) {
    if (p.moveAmp <= 0) continue
    const half = Math.max(1, p.movePeriod / 2)
    const t = (w.frame + p.movePhase) % p.movePeriod
    const k = t < half ? t / half : 2 - t / half        // 0→1→0 的三角波
    p.x = p.baseX + (k * 2 - 1) * p.moveAmp
  }
}
```

**必须用三角波而不是正弦**：`Math.sin` 违反铁律 L2（见 [服务端与联机](./05-server.md) 第 3 章），
而三角波只有加减乘除，确定性天然成立。代价是运动有"折角"，但 300 帧一个往返、
振幅 130px 的平台上，折角在视觉上完全看不出来——**用绝对值最便宜的确定性换掉了一个
最容易 desync 的点**。

**移动必须在每帧的物理之前算完**：`updateMovingPlatforms` 是 `step()` 的第一个物理动作。
如果放在角色移动之后，这一帧角色就站在"上一帧的台面位置"上，
高速移动时会出现角色脚底与台面错开 1–2px 的抖动。

**站在平台上的角色不被动携带**——v1 刻意不做"吸附"。理由是：携带需要额外记录
`ridingPlatformId` 并进快照，而"平台把人推着走"这件事在低振幅下几乎没人察觉；
等 v2 真要做高速移动台时再加，那时才需要这个字段。

## 4. 出界判定（Blast Zone）

### 4.1 判定逻辑

```ts
export function checkBlast(w: World, stage: StageDef): void {
  const b = stage.blastZone;
  for (const f of w.fighters) {
    if (!f.active) continue;
    if (f.x < b.x || f.x > b.x + b.w || f.y < b.y || f.y > b.y + b.h) {
      w.stocks[f.id]--;
      f.active = false;
      f.damage = 0;                              // 下一命从 0% 开始
      f.respawnTimer = RESPAWN_DELAY_FRAMES;     // 100
      w.events.push({ t: 'ko', fighter: f.id, x: f.x, y: f.y });
    }
  }
}
```

### 4.2 为什么用中心点，不用包围盒

- **体型公平**：包围盒判定下，半宽 24 的角色比半宽 18 的角色早 6px 出界。体型变成了隐藏属性，同一个击飞值打出不同结果，这在 1v1 里是致命的。
- **不会「看起来还没出去」**：盒子边缘已经越界、而角色视觉上还在画面里就判负，玩家会当成 bug。这是最容易被投诉的体验点。
- **唯一基准**：中心点就是速度与重力积分的那条轨迹，判定和物理共用同一个数，不需要额外的尺寸常量。
- **代价**：中心点越界时还有半个身子可见。用 4 帧 KO 特效（白闪 + 定格）盖住这段，而不是把判定改回包围盒。

### 4.3 推荐尺寸

| 参数 | 值 | 推导 |
|---|---|---|
| 水平边距 | 370px | 一次全跳的水平位移 ≈ 29 帧 × 9px ≈ 260，再留 110 缓冲 |
| 上边距 | 台面上方 760px | 4.4 × 二段跳高度（172），保证高空击杀有滞空观赏 |
| 下边距 | 台面下方 480px | 复归总高度 ≈ 二段跳 172 + 上 B 约 180 = 352，超过 480 基本无望 |
| 场地横向总宽 | 2240px | 主台 1500 + 2 × 370 |

### 4.4 blastZone 必须比相机视野大（v0.10 已放大）

> **v0.10 起口径变了**：`cameraBounds` 字段已删除，相机范围改为从「场地 ∪ blastZone」推导。四张图的 blastZone 统一放大到 `3440×1880` 量级（v0.10.2 再次外扩），侧向空白带约 900px。理由见 §7.5：要满足「场地完整可见 + 视口不越界」两条约束，缩放必须落在 `[view/blast, view+2·pad)/stage]` 之间，边界太窄会把这个区间压空。代价是 KO 距离变远（残灯台 1120→1420→1720），实测评测：从主台右沿起打，`80% → KO@129f`、`150% → KO@86f`、`200% → KO@63f`，仍然打得出去，只是飞行过程更戏剧化，所以 `KNOCKBACK_TO_SPEED` 保持 0.09 未改。



相机拉到最远时视野宽 `1280 / 0.67 ≈ 1910px`，而 blastZone 宽 2240px——差的 330px 就是「安全边」。玩家被击飞时最重要的信息是**方向**：从哪个角度飞出去、还剩多少距离、该往哪边 DI。如果镜头先到边、人被直接删除，玩家会觉得「凭空消失」，这一局他学不到任何东西。

硬约束写进 loader 校验：`blastZone.w ≥ (VIEW_W / ZOOM_MIN) * 1.10`（1910 × 1.10 = 2101 ≤ 2240 ✓）。

## 5. 场地事件（Hazards）

场地事件是「这张图不只是背景」的全部来源。它的设计约束只有一条：**可预测、可回避、不替玩家做决定**。

### 5.1 五种事件

| `kind` | 表现 | 伤害 | 机理 | 代表场地 |
|---|---|---|---|---|
| `flame` | 地面喷口周期性喷火柱 | 9% | 矩形触发，`duration` 内持续生效 | 灰烬原 |
| `lava` | 底部岩浆上涨退去 | 14% | 大矩形，长周期，逼人往上打 | 灰烬原 |
| `gear` | 横向滚动的旋转齿轮 | 12% | 沿 x 做三角波扫描，扫到谁打谁 | 齿轮工坊 |
| `rock` | 从上方落石 | 11% | 抛物线，`animate` 用 `t²` 加速 | 天穹回廊 |
| `wind` | 上升气流 | **0** | 只推不伤：把 `vy` 抬到固定值 | 天穹回廊 |

前四种是「惩罚站错位置」，`wind` 是唯一一种**纯增益**事件——它不打人，只改变机动。
一张图里放一个纯增益事件，能让「站在这里」变成战术选择而不是躲灾。

### 5.2 周期与相位

```ts
export interface HazardState {
  def: HazardDef          // 只读定义
  x: number; y: number    // 运行时位置（gear 会移动）
  t: number               // 在本周期内的帧号
  active: boolean
}
```

判据只有一个：

```ts
const t = (w.frame + d.phase) % d.period
const active = t < d.duration
```

`phase` 就是**错开相位**用的。灰烬原三个火口用 `phase 0 / 100 / 200`、`period 300`、`duration 80`——
任何时刻至多两个在喷、任何一个都在 300 帧（5 秒）内必然喷一次。**5 秒是人类能记住的周期上限**，
再长玩家就不建立了预期，事件会退化成"随机受伤"。

`w.frame % period` 这个写法是刻意选的：它把事件完全绑定在逻辑帧上，于是事件天然确定、
天然进校验和、天然能被回放复现。**不要用 `Date.now()` 或渲染时钟做事件驱动**——
那样两台机器上的地火永远不同步。

### 5.3 为什么伤害这么低

场地事件伤害全部在 9–14% 之间，远低于普通攻击的 10–20%。原因：

- **事件的作用是改变站位，不是造成伤害。** 它的威胁在于「你必须离开这里」，
  12% 的伤害只是为了让你真的离开，而不是为了赢。
- **如果用场地杀人，胜负就不掌握在玩家手里。** 一个 30% 伤害的地火会让人觉得
  「我不是被打死的，是被地图打死的」，这是平台格斗里最差的一种失败体验。

对应的硬上限：**任何单个事件一次最多造成一个角色 15% 伤害，且 `HAZARD_IFRAMES = 18`
保证不会被同一事件连续多帧命中**（否则站在地火里 80 帧会掉 80 × 9%）。

### 5.4 击飞方向

事件伤害不是"扣血"，是**按角度击飞**——和普通攻击走同一个 `applyHit`：

| 事件 | `angle` | `baseKB` | 意图 |
|---|---|---|---|
| `flame` | 90（垂直上） | 24 | 抛起来，给你空中挣扎的机会 |
| `lava` | 90 | 30 | 抛得更高，因为伤害也更高 |
| `gear` | 水平（按扫描方向） | 26 | 横推，靠位置打人 |
| `rock` | -80（斜下） | 22 | **往下砸**，最危险——直接送向底部出界 |
| `wind` | — | — | 不击飞，只抬升 |

`rock` 用向下角度是全场唯一"往出界方向打"的事件。它出现在天穹回廊的两条窄桥上，
配合桥本身可被打碎，形成「桥在碎、石头在往下砸」的复合压力。这是四张图里唯一
可以**被场地直接杀死**的地方——但即便这样，玩家仍有 22 的 `baseKB` 和一次空中冲刺可以逃。

### 5.5 视觉必须早于判定

事件的判定区在 `active` 为真时瞬间生效，但**视觉必须提前预告**：

| 阶段 | 帧数 | 表现 |
|---|---|---|
| 预告 | `duration` 之前 18 帧 | 喷口发光/齿轮走近/头顶投影 |
| 激活 | `duration` | 实体特效 + 判定生效 |
| 余韵 | 之后 10 帧 | 特效淡出，判定已关 |

18 帧 = 0.3 秒，是人类对"即将发生"的典型反应时间。少于 12 帧玩家来不及动，
多于 24 帧玩家会开始忽略它。**预告帧数不进模拟状态**，它是渲染层根据
`def.period/phase/duration` 从 `w.frame` 算出来的——模拟只关心 `active`。

## 6. 复活系统

### 6.1 时间线

| 帧 | 事件 | 状态 |
|---|---|---|
| 0 | KO 判定，`stocks--`，伤害归零 | `Inactive` |
| 0–99 | 等待（`RESPAWN_DELAY_FRAMES=100`），相机改为单人框选 | `Inactive` |
| 100 | 在选定 spawnPoint 生成复活平台 + 角色 | `Respawn` |
| 100–159 | 无敌 60 帧（`RESPAWN_INVINCIBLE=60`） | `Respawn` |
| 100–339 | 平台最多存在 240 帧 | `Respawn` |
| 任意 | 按下 / 跳 → 离开平台 | `Fall` |
| 340 | 平台消失，角色强制下落 | `Fall` |

### 6.2 机制

- 复活平台**不是** `StageDef.platforms` 的成员。它由 `World.respawnPlatforms[]` 每帧生成动态 AABB。理由见 §12.3：`StageDef` 必须只读、可哈希，塞进动态平台就毁了这一点。
- 站在平台上时 `grounded = true`、`platformId = -2`（负数段保留给运行时平台，`-1` 是「空中」）。
- 无敌严格按帧计时到 0，**不随停留延长**。想赖在台上就得承担 60 帧后仍停在原地的风险。
- 平台宽 160px（角色 40px 宽的 4 倍），允许在上面走两步调整落点。

### 6.3 位置选择

`spawnPoints` 三个点：`x = -330 / 0 / +330`，`y = -340`。

- 默认中位。复活延迟的 100 帧内按左右可循环切换（左位再按左 → 回中位）。
- 切换立即生效，角色与平台一起水平移动；**落地后锁定**，不能在空中改。
- 三个点横跨 660px，守方无法同时覆盖两侧，必须读人——复活阶段本身是一次小博弈。

### 6.4 为什么复活点在主台上方，而不是屏幕中央

- **屏幕中央是相对的**。相机的目标中心正是两名角色的包围盒中点，也就是说「屏幕中央」经常就是两人中间、离对手最近的那块区域。把复活点放那儿等于直接把人送到对手面前。
- 主台上方 `y=-340` 是**绝对坐标**，距台面 340px，按 `MAX_FALL=12` 下落需 28 帧（0.47s）。这半秒里复活方看清局势，守方也能预判落点，双方都有事可做。
- `-340` 高于所有副台（最高 `-150`），保证复活不会被副台挡住视线，也不会一出现就落在别人的平台上。
- 复用同一套坐标还能让相机逻辑更简单：复活期间视野不需要特殊偏移。

### 6.5 相机配合

复活期间只有一名 active 角色，包围盒塌成一个点会让缩放顶到上限。所以 `Respawn` 阶段把 `ZOOM_MAX` 临时压到 1.00，避免复活瞬间视野突变。

## 7. 相机系统

平台格斗的相机要同时满足三件事：两个人都看得见、不乱晃、不露馅。它不是「跟随主角」，而是**一个由双方位置共同决定的函数**。

### 7.1 双人框选

```
box    = (maxX - minX, maxY - minY)           // 含头顶；宽高各设下限 minBoxW/minBoxH
zoom   = clamp(min(VIEW_W / (boxW + 2*PAD_X/zoom), VIEW_H / (boxH + 2*PAD_Y/zoom)), ZOOM_MIN, ZOOM_MAX)
center = ((minX + maxX) / 2, (minY + maxY) / 2)
```

`PAD_X = 170`、`PAD_Y = 130`，给击飞弧线留出「还能看到落点」的空间。只统计存活角色（`respawnTimer <= 0`）。

**边距是屏幕像素，不是世界单位。** 这是第一版最容易写错的地方：写成世界单位时，镜头拉远后边距在屏幕上会跟着缩小，玩家会觉得「人都快贴边了还不框进来」。屏幕单位则不管怎么缩放，两人离边框永远这么远。

代价是出现了一个循环依赖——边距换算成世界单位要除以缩放，而缩放又依赖边距。**做两次不动点迭代就收敛**（`PAD/zoom` 的量级是几百像素，两次足够；实测第三次迭代的变化 < 0.5px）：

```ts
let wantZoom = cam.zoom
for (let i = 0; i < 2; i++) {
  const padW = (PAD_X * 2) / wantZoom
  const padH = (PAD_Y * 2) / wantZoom
  wantZoom = clamp(Math.min(VIEW_W / (boxW + padW), VIEW_H / (boxH + padH)), ZOOM_MIN, ZOOM_MAX)
}
```

**包围盒宽高要有下限**（`minBoxW = 140`、`minBoxH = 96`）。两人重叠时包围盒会塌成 0，缩放冲到 `ZOOM_MAX`；一旦稍微分开又猛缩回来——那种「吸一口气再吐出去」的镜头比不缩放还难看。

### 7.2 死区 + 距离自适应跟随

- **死区 56×40**：目标中心落在死区内就不推动镜头。角色原地受击抖动、走路起步都不会晃镜头。
- 死区外不直接对齐，而是**先把目标压回死区边界，再用随距离放大的系数 lerp**：

```ts
const dist = Math.hypot(dx, dy)
const k    = clamp(0.09 + (dist / 420) * 0.34, 0.09, 0.43)   // 近→0.09，远→0.43
const step = Math.min(4, dtMs / C.STEP_MS)                   // 本帧包含几个逻辑步
const alpha = 1 - Math.pow(1 - k, step)                      // 多步合并成等效系数
```

**为什么系数要随距离变**：固定系数在「两人贴身」时太慢（镜头总在追一个刚离开的点），在「一人被击飞到屏幕另一头」时也太慢（要 60 帧才追上，人已经出画了）。按距离插值让近处稳、远处快——**过渡时长随距离缩短，观感才是"速度一致"而不是"时长一致"**。

**为什么要归一化到逻辑步**：渲染帧率不一定是 60（144Hz 一帧可能跑 0 个逻辑步，掉帧时一帧跑 2–3 步）。直接用 `k` 的话 144Hz 下镜头会快 2.4 倍。归一后**镜头位置是逻辑步数的函数而不是渲染帧数的函数**。

### 7.3 前视（lead）

```ts
const leadX = clamp((vxSum / n) * LEAD_TIME * 60, -LEAD_MAX_X, LEAD_MAX_X)   // 0.18s
const leadY = clamp((vySum / n) * LEAD_TIME * 60, -LEAD_MAX_Y, LEAD_MAX_Y)
tx = (minX + maxX) / 2 + leadX
ty = (minY + maxY) / 2 + leadY
```

没有前视时，镜头永远是「被拖着走」：人已经飞到画面边上，镜头才开始追，玩家看到的是自己的角色贴着边框。按两人**平均速度**（不是各自速度）提前 0.18 秒，既不会因为一人冲刺就把画面拽走，又能让整体移动方向上的留白提前出现。

`LEAD_MAX_X = 96` / `LEAD_MAX_Y = 56` 是上限：不夹的话一次高速击飞会把镜头甩出去半屏。

### 7.4 缩放：死区 + 非对称速度

```ts
if (Math.abs(wantZoom - cam.zoomTarget) > ZOOM_DEADBAND) cam.zoomTarget = wantZoom  // 0.035
const zk = cam.zoomTarget < cam.zoom ? 0.30 : 0.10   // 拉远快、推近慢
cam.zoom += (cam.zoomTarget - cam.zoom) * (1 - Math.pow(1 - zk, step))
```

两条都是必须的：

1. **死区**：两人距离小幅来回（连打、小跳、原地 dash）会让 `wantZoom` 每帧抖动，没有死区时画面持续「呼哧呼哧」地泵。0.035 换算到缩放上大约是 3% 的视野变化，肉眼看不出，但足以吃掉抖动。
2. **非对称**：拉远慢了会有人出画（功能性问题），推近快了会晕（体验问题）。所以拉远用 0.30、推近用 0.10——**三倍差**。

### 7.5 边界钳制

`cameraBounds` 夹的是**相机中心**，而允许范围必须按当前缩放的**半视野**算：

```ts
const halfW = VIEW_W / 2 / zoom
const halfH = VIEW_H / 2 / zoom
minX = b.x + halfW;  maxX = b.x + b.w - halfW
```

第一版用了固定的 `±640`，那只在 `zoom = 1` 时成立。`zoom = 0.62` 时半视野是 1032，固定夹会让画面越界 392px——表现就是「镜头已经贴住场地边界，画面里却还露着场地外的空白」。这类错误静止看永远发现不了，一跑缩放就露馅。

**视野比场地本身还宽时夹不住**，此时退化为「对准场地中心」（区间收缩成一个点）。

另外，**缩放变过之后要再夹一次**：可动范围随缩放变化，不重夹就会出现「镜头合法但画面越界」的一帧。

美术交付的覆盖范围仍然按最小缩放算：**背景范围 = cameraBounds 外扩 `ceil(VIEW_W/2/ZOOM_MIN) = 1032` 横向、`ceil(VIEW_H/2/ZOOM_MIN) = 581` 纵向**。以本图为例：`x ∈ [-1552, 1552]`、`y ∈ [-841, 721]`。

### 7.6 为什么震动必须在表现层

| 项 | 模拟层（`World`） | 表现层（`Renderer`） |
|---|---|---|
| 相机位置 / 缩放 | ✓ 进快照 | 只读 |
| 震动偏移 | ✗ | ✓ 每帧随机，叠加在渲染相机上 |

1. 震动是**高频噪声**，进快照就是每帧多两个浮点数，回滚重演时噪声序列根本复现不了（它来自渲染时钟），只会让画面抖两次。
2. 震动不影响任何判定：hitbox、抓边、复活、出界，没有一个读它。没有同步需求的东西不该进同步状态。
3. 实现：`renderCamX = w.cameraX + shakeX`；`shakeX/Y` 由渲染层独立的 PRNG（固定种子，例如 `0x9E3779B9`）生成，每帧衰减 `0.88`，幅度上限 14px，命中时按伤害注入 4–10px。

### 7.7 为什么相机应该放在 World 里

- **两端必须一致**：相机定义了「屏幕外」这个概念，而屏幕外提示箭头、抓边时的镜头偏移都依赖它。若 A 端认为对手在屏幕外、B 端认为在屏幕内，同一帧的输入语义就不同了。
- **回滚可重演**：相机在 `World` 里，回滚 N 帧后重演得到同一相机。若相机只在渲染层平滑，回滚会看到镜头「闪回」再「追回去」。
- **代价可忽略**：每帧 3 个 double 进快照，相比角色十几个字段不值一提。
- **shake 不在**：见 7.6，它是纯观感，且随机源必须和模拟随机源隔离（不能消耗 `w.rngState`，否则回滚后所有随机判定都会错位）。

| `padStageX` / `padStageY` | 40 / 34 | 全员在场地上时的留白（**屏幕像素**） |
| `padFighterX` / `padFighterY` | 96 / 86 | 有人出场时的留白 |

### 7.5.1 为什么镜头会「一张一缩」——以及三条止抖措施

第一版镜头在实战里有一个明显毛病：**画面持续地放大缩小**，一记上挑就缩一下再弹回来。三个独立的成因，各自要一条对策。

**成因一：拿当帧的角色位置反推缩放。** 角色一帧能被击飞几十像素，盒子跟着每帧变化，缩放就每帧追一次。

> **对策：取景框低通。** 相机自己存一份平滑盒子（`cam.bx0/bx1/by0/by1`），每帧朝当帧真实盒子靠 `boxK = 0.16`。缩放只跟得上"趋势"，跟不上"抖动"。
> 同时保留**单向兜底**：真实盒子比平滑盒子大时直接把那一侧推出去——宁可跳一下也不能把人丢出画面。

**成因二：留白是二值切换。** 原写法是"有人出界就换成大留白"，于是角色跨过场地边线那一帧，留白从 40 跳到 96，缩放立刻跳。

> **对策：留白连续化。** `padBlend = clamp(越界距离 / 240, 0, 1)`，留白在两个值之间线性插值。跨线不再是阶跃，而是渐变。

**成因三：推近没有迟滞。** 打完一套回到站桩会立刻推近，下一个连段又拉远——这就是"泵"。

> **对策：拉远立刻、推近等一等。**
> · 目标缩放 < 当前 − 0.004：**立刻**跟（拉远是安全方向，晚一帧就可能有人出画）；
> · 目标缩放 > 目标 + `zoomInThreshold 0.08` 且**连续 26 帧**都满足：才允许推近；
> · 其余情况保持不动，`zoomHold` 缓慢回落。

**还有一个隐患：可动范围是缩放的函数。** `camBounds` 随 zoom 变，平滑盒子滞后时范围会突然变窄，硬夹等于把相机一帧拽几百像素。

> **对策：三处限速 + 出口总限速。** 可动范围收敛做限速（200px/帧）、出界兜底做限速（140px/帧），最后在 `stepCamera` 出口统一把"这一帧总共走了多远"夹到 **210px**。单帧位移是"看起来会不会像瞬移"的唯一判据，所以必须有一处总闸。

对应断言（`tools/check-camera.mjs` 第 11 组）：

```
✓ 小起伏不缩放（累计行程 < 0.02）      行程=0.0000
✓ 大起伏跟得上且不抽（600 帧反转 <= 14 次）  反转=0
✓ 单帧位移有上限（不瞬移）             最大 210.6px/帧
```

### 7.9 实现位置与可断言性

镜头数学全部在 `packages/client/src/game/cameraRig.ts`，是**纯函数**（不 import `protoRuntime`，只接收结构化的 `CamWorld`）。

```ts
export function createCam(y?: number): CamState
export function computeCameraTarget(w: CamWorld, cam: CamState, tune?: CamTuning): CamTarget
export function stepCamera(cam: CamState, w: CamWorld, dtMs: number, tune?: CamTuning): CamTarget
export function camBounds(w: CamWorld, zoom: number, tune?: CamTuning): { minX; maxX; minY; maxY }
export function screenOf(cam: CamState, wx: number, wy: number, tune?: CamTuning): { x; y }
export function offscreenOf(cam: CamState, f: CamFighter, margin: number, tune?: CamTuning): { dirX; dirY } | null
```

**为什么要抽成模块**：镜头的正确性可以脱离画面被断言。留在 `.vue` 里就只能靠眼睛看，而眼睛看不出「144Hz 下镜头比 60Hz 快一倍」。

`tools/check-camera.mjs` 的九组断言：

| # | 断言 | 抓的是什么 |
|---|---|---|
| 1 | `crouchH == C.CROUCH_HEIGHT`、视口 1280×720 | 常量两处漂移 |
| 2 | 两人都在画面内 | 缩放反推算错 |
| 3 | 画面不露出场地的 cameraBounds 外 | 固定 ±640 夹的越界 |
| 4 | 60Hz 与 144Hz 跑同一秒结果一致 | 帧率依赖 |
| 5 | 单帧位移 < 220px | 瞬移 |
| 6 | 10px 扰动下镜头不动 | 死区失效 |
| 7 | 相距 3000px 时至少一方判出画；近距离不误报 | 出界判定 |
| 8 | 缩放恒在 `[min, max]` 且无 NaN | 迭代发散 |
| 9 | `camBounds` 区间随缩放收窄 | 边界换算 |

### 7.10 出界指示器（镜头装不下时的兜底）

镜头有一条物理上做不到的事：**两人离得比 `ZOOM_MIN` 允许的视野还远时，一定有人出画**。`ZOOM_MIN = 0.62` 的视野是 2064 × 1161 世界单位，而场地加出界区可以到 2240 宽——一人被击飞到场地另一端复归时就会超出。

大乱斗的处理方式不是继续拉远（再远就变成俯瞰小点了），而是**在画面边缘画一个指向他的箭头 + 他的伤害值**。本项目照做（`drawOffscreenCues`）：

- 判定：`offscreenOf(cam, f, 26)` 用角色胸口点算屏幕坐标，出 `[26, W-26] × [26, H-46]` 即判出画。
- 箭头：把屏幕坐标夹进内边界得到锚点，画一个沿「真实方向」旋转的三角，透明度 `0.55 + 0.45*|sin((frame + i*23)*0.07)|` 呼吸。
- 徽章：锚点内侧 26px 处一个深色圆 + 伤害值，颜色按槽位（`#3b82f6` / `#f97316`，与 HUD 一致）。
- **画在最上层**（`drawComboText` 之后）：它是「找不到人」时唯一的线索。

### 7.11 关于「相机放在渲染层」的取舍（原型现状）

§7.7 论证过相机**应该**在 `World` 里（联机两端一致、回滚不闪回）。**v1 原型仍把它放在渲染层**，这是有意为之的临时决定：

| | 相机在 `World` | 相机在渲染层（原型现状） |
|---|---|---|
| 确定性 | 天然（进快照进校验和） | 不影响——镜头不参与任何判定 |
| 依赖相机的机制 | 屏幕外箭头、抓边镜头偏移 | **箭头已实现，但只画不改判定** |
| 联机 | 两端必然一致 | 两端可能不同（只影响观感） |
| 好处 | 回滚时不闪回 | 可以用真实 `dtMs` 做帧率无关平滑，不必为了确定性放弃 |

关键判断：**出界箭头虽然读相机，但它只影响"看到什么"，不影响"能做什么"**。只要没有「看不见就不能出招」「镜头外不结算」这类规则，渲染层相机就是安全的。

一旦出现下面任一条，就必须把相机搬回 `World`，并同时放弃 `dtMs` 平滑、改成固定系数的逻辑步驱动：

- 屏幕外的角色不结算命中（防偷打）
- 抓边成功时镜头偏移会改变玩家输入时机
- 联机对局需要双方对「谁在屏幕外」达成一致

### 7.12 与本文其他章节的关系

- §7.6 讲**为什么震动不在模拟层**，那一条至今不变。
- §7.8 的参数表已按 v0.8.2 实现更新（旧版本是死区 60×44、边距 150/120、固定 ±640 夹）。
- 背景美术的覆盖范围按 §7.5 的 `ZOOM_MIN` 反推，不要按 `ZOOM_MAX`。

## 8. 示例场地「残灯台」

### 8.1 设计意图

断崖上的一座废弃灯塔。主台是一整块平整的混凝土基座（无斜坡、无洞、无台壁拐角），三块锈蚀的钢架平台悬在基座上方：两侧各一块低台，正中一块高台。灯塔本身站在背景层左后方，不与玩法区重叠。

三层结构对应三种战斗方式：**地面立回**（主台）、**中空机动**（侧台）、**高点压制**（中台）。三层之间是均匀的 75px 高差——刚好一个全跳的 87%，跳得上去但必须读距离。

**齿轮工坊**（`gearworks`，danger 2）——验证「地形会动」

| 项 | 值 |

两台齿轮 `phase` 相差 120 帧（半周期），保证任何时刻只有一侧有齿轮，永远有一条安全路线。

**灰烬原**（`ember_field`，danger 3）——验证「必须换站位」

| 项 | 值 |
|---|---|
| 主台 | `solid` `1400×120`（比基线窄 100） |
| 侧台 | 2 × `passthrough`，`hp=30` / `respawn=300`（最脆） |
| 事件 | 3 × `flame`（`period=300`、`phase=0/100/200`、`duration=80`、`damage=9`、`x=-480/-30/420`）+ 1 × `lava`（`period=900`、`phase=400`、`duration=220`、`damage=14`、`y=140`、`h=160`） |
| `blastZone` | `x=-1000 y=-700 w=2000 h=1140`（**比基线小**） |

设计意图：主台窄 + 出界近 + 地火周期，把「站着打」变成「边打边挪」。这是四张图里
唯一会让人主动往副台跑的。三个火口相位差 100 帧，任何时刻至多两个在喷。

**天穹回廊**（`sky_bridge`，danger 2）——验证「地形会消失」

| 项 | 值 |
|---|---|
| 主台 | **不存在**。两条 `solid` 窄桥各 `300×26`、`grabbable`、`hp=52` / `respawn=480` |
| 移动台 | 中间 1 块 `passthrough` |
| 事件 | 1 × `wind`（0 伤害，托人）+ 2 × `rock`（`period=220`、`damage=11`、`angle=-80`） |

设计意图：**把「主台一定存在」这个默认打破**。两条桥都能被打碎，碎了之后没有任何落脚点——

`rock` 的 `angle=-80`（斜向下）是全场唯一往出界方向打的事件，配合"没有主台"的几何，
构成最高压力的组合。但即便如此，玩家仍有 22 的 `baseKB` 与至少一次空中冲刺可以逃——
**压力要给到"必须做对"，不能给到"做对也没用"**。

## 9. 场地与玩法的互动

### 9.1 v1 实际做了四张，但只有一张是基线

v0.5.0 之前这一节写的是「v1 只做一张场地」，理由是工期与回归成本。**v0.6.0 起改成四张**，
但那条理由并没有作废，只是被重新组织成了优先级：

| 场地 | 危险 | 角色 | 定位 |
|---|---|---|---|
| 残灯台 | 1 | **基线图** | 一切物理/击飞参数都在它上面调；复归验收也只在它上面跑 |
| 齿轮工坊 | 2 | 移动平台 + 齿轮 | 验证「地形会动」这一件事 |
| 灰烬原 | 3 | 周期地火 + 熔岩 | 验证「必须换站位」这一件事 |
| 天穹回廊 | 2 | 可破坏窄桥 + 落石/上升气流 | 验证「地形会消失」这一件事 |

**每张图只验证一个新的机制**，这是那三条旧理由的延续：

- **一个可回归的基线**：物理和击飞参数每改一次，只有残灯台需要全量复测；另外三张只跑
  「该图特有机制」的断言（`tools/check-combat.mjs` 第 27 组：四张场地各跑 600 帧不崩）。
  十张图就是十倍的回归成本，所以宁可四张图各只负责一件事。
- **社区共识**：格斗游戏「一张图打 1000 局」比「十张图各 100 局」更容易形成稳定的对局认知。
  所以四张图里有三张是「可选的调味」，排位默认图仍然是残灯台。
- **工期**：残灯台之外的每张图按 1–2 天算（数据结构已经支持，只是填 JSON + 跑一遍断言）。

### 9.2 常见场地类型对比

| 类型 | 结构 | 优点 | 缺点 | 复归难度 |
|---|---|---|---|---|
| **终点型** | 平坦主台 + 对称单层副台 | 最中立，地形几乎不参与胜负 | 观赏性略弱，翻盘手段少 | 中 |
| **三角形副台型** | 两低一高，三块构成三角 | 垂直连段丰富，追打路线多 | 高点压制过强，落点过于单一 | 高 |
| **三平台型** | 三层阶梯叠放 | 移动路线最多，观赏性好 | 新手容易迷失，边缘视野差 | 中高 |
| **有坑型** | 主台开洞 | 地形杀、心理战 | 需要「洞边抓边」逻辑，v1 物理不支持 | 极高 |

四张图全部落在**终点型 / 三平台型**这两类里，没有一张做「坑」：

- 齿轮工坊 = 终点型 + 移动台。移动台是**唯一一种不改变地形拓扑就能改变节奏**的机制。
- 灰烬原 = 终点型 + 事件。地形完全平坦，压力全部来自时间轴而不是空间。
- 天穹回廊 = 三平台型 + 可破坏。两条 `solid` 窄桥打破「主台一定存在」这个默认，
  但它仍然是两块矩形——**不是坑**。坑需要「洞边抓边」这种新物理，那是 v2。

### 9.3 为什么基线图选终点型

- 平坦主台是物理 bug 最容易暴露、也最容易复现的几何。先在它上面把扫掠、抓边、出界调对，再谈地形。
- 对称副台只验证「单向平台」这一件事，不引入斜坡、坑、台壁拐角三种额外情况。
- 复归验收只有两个边缘、两条路线，M5 的验收单能在一小时内跑完。
- **术语说明**：社区里「终点」通常指零副台。本文沿用总纲 [D4 决策](./00-overview.md) 的叫法，指「主台平坦、副台全对称、无特殊地形」。D4 记录的是「平地 + 2 个旁台」，这里用 4 块（多一块中台），因为它同时验证多层单向平台与垂直机动。若评审要求严格零副台，删掉 `platforms[1..3]` 即可，**代码零改动**——这就是数据驱动的价值。

### 9.4 数据驱动的边界

- 换图 = 换一个 `StageDef`。`World` 里只存 `stageId`，快照体积不变。
- **选图 UI 已实现**（`packages/client/src/views/StageSelectView.vue`）：左侧四张图竖直列表、
  中间按**每张图自己的 `blastZone`** 反算预览缩放、右侧情报卡（平台数/可抓边/可破坏数/
  移动台数/事件列表）。这是 v0.6.0 才补的——在此之前是写死一张图。
- 预览缩放必须按各自的 `blastZone` 算：四张图的 `blastZone.w` 不同（残灯台 2240、灰烬原 2000、
  天穹回廊更小），用固定常量会让有的图塞不满、有的图溢出框。
- v1 **仍然不做图形化地图编辑器**（理由见 §11.4），四张图都是手写 JSON + loader 校验。

## 10. 美术与背景层

### 10.1 分层

| 层 | 视差 `p` | 内容 | 说明 |
|---|---|---|---|
| L0 `sky` | 0.00 | 天光渐变、静态云 | 完全固定，不随缩放变化 |
| L1 `sea` | 0.10 | 海平线、远处灯影 | 微动，制造纵深 |
| L2 `cliff` | 0.30 | 断崖剪影 | 中景 |
| L3 `beacon` | 0.55 | 废弃灯塔塔身 | 与主台在视觉上「接」在一起 |
| L4 `mist` | 0.75 | 雾带 | 分隔中景与玩法区 |
| L5 `rain` | 1.00 | 雨丝 | 与玩法区同速，但不覆盖角色 |
| L6 `fg` | 1.20 | 前景浪花 / 飞鸟 | 只在屏幕四边，禁止进入中间 70% 区域 |

### 10.2 视差公式

```
screenX     = VIEW_W / 2 + (worldX - cameraX) * zoom * p
screenScale = 1 + (zoom - 1) * p
```

- `p=0` 时屏幕位置固定，且不随缩放放缩——天空不该跟着镜头缩放。
- `p=1` 时与世界完全同步。
- **必须乘 `zoom`**。漏乘的话，缩放时近层放大、远层不变，透视立刻错乱，玩家会觉得「背景在滑」。

### 10.3 背景动画帧率可以低于 60

- 背景动画 8–24fps（`frameIndex = ((t * fps / 1000) | 0) % frames`），与 60Hz 逻辑帧解耦。
- 用渲染时钟（`performance.now()`）驱动，**不读 `World.frame`**。
- 为什么不影响确定性：背景只在渲染层，不进快照、不参与碰撞。两次渲染的动画相位不同完全无所谓。
- 反过来的红线：**一旦把背景动画写进 `World`，它就会进快照**——禁止。同理，背景层不允许有 `Math.random()` 的模拟副作用（渲染层的随机只影响像素）。

### 10.4 角色辨识度

| 规则 | 阈值 | 检查方式 |
|---|---|---|
| 明度差 | 角色平均亮度与背景 ≥ 25%（HSL 的 L） | 截屏取 10 个采样点算均值 |
| 背景饱和度 | 玩法区 S ≤ 40% | 吸色器抽查 |
| 高频细节 | 玩法区内禁止 4px 以下的碎纹理 | 会淹没角色轮廓 |
| 轮廓 | 角色 2px 深色描边（alpha 0.55） | 在 L3 层前面上做对比 |
| 色相 | 背景整体偏冷（+15°），角色保持原色 | 对手方用暖色技能时尤其重要 |
| 平台对比 | 台面与背景至少差 2 个亮度级 | 站台边时不能「消失」 |

### 10.5 背景配置类型

```ts
export interface BackgroundDef {
  layers: BgLayer[];
  tint: string;          // "#RRGGBB"，整体叠色（Pixi 8 的 tint 接受字符串）
  ambient: number;       // 0..1，环境光强度，渲染层乘到角色上
}

export interface BgLayer {
  id: string;
  texture: string;       // 资源键，加载期解析
  parallax: number;      // 0..1.2，0 = 固定，1 = 与世界同速
  scale: number;
  offsetX: number;
  offsetY: number;
  tint?: string;
  alpha?: number;
  depth: number;         // 绘制顺序，小的先画
  anim?: { frames: number; fps: number; loop: boolean };  // fps <= 30
}
```

## 11. 场地数据的工作流

### 11.1 流程

纸面推演（尺寸表 §8.2）→ 手写 JSON → loader 校验 → 调试可视化器 → 试玩调参 → 回归测试（复归 240 帧 + 盲区检查 + 穿模计数归零）。

### 11.2 loader 校验清单

| 检查 | 失败后果 |
|---|---|
| `id` 从 0 连续递增 | `platformId` 索引错位，站台判定串台 |
| 平台两两不重叠（面积重叠 > 80% 报错） | 站在重叠区会反复换台，抖动 |
| `blastZone` 包含所有平台 | 平台在界外 = 站上去立刻死 |
| `cameraBounds ⊂ blastZone` | 镜头拍到界外，露馅 |
| `spawnPoints` 在 blast 内且高于所有副台 | 复活卡在平台里 |
| `grabbable` 平台至少 1 个、抓边点至少 2 个 | 无复归点，对局无法进行 |
| 副台层高 ≤ 全跳高度 × 0.95 | 跳不上去的副台等于装饰 |

### 11.3 调试可视化器功能清单（开发期必须有）

- [ ] 平台矩形按类型着色：`solid` 白 / `passthrough` 黄 / `ceiling` 青，1px 描边
- [ ] 每个平台标注 `id` 与 `thickness`
- [ ] 抓边点画 6px 圆 + `GRAB_RADIUS` 圈 + 朝向箭头
- [ ] `blastZone` 红框、`cameraBounds` 黄框、当前视野绿框三层叠加
- [ ] 相机中心十字与死区矩形
- [ ] 角色 AABB + `prevX/prevY` 到当前位置的连线（看击飞弧线）
- [ ] 扫掠分步：每个 `maxStep` 子步画一个点（诊断穿模的唯一手段）
- [ ] 数值面板：`frame / x,y / vx,vy / state / grounded / platformId / zoom`
- [ ] 穿模检测：角色 AABB 与任一 `solid` 重叠 → 红色闪烁 + 计数器
- [ ] 热重载：改 JSON 不重启，直接重建 `StageDef`
- [ ] 单帧步进 + 拖时间轴（配合 netcode 的快照回放）
- [ ] `F1` 总开关，`F2` 只显示碰撞层（关掉美术）

### 11.4 为什么不做图形化地图编辑器

- v1 只有一张图，编辑器的成本（拖拽、吸附、撤销、序列化、冲突检测）大约是这张图调参时间的 3 倍。
- 手写 JSON + 可视化调试器已经覆盖「改了就能看见」，效率瓶颈不在输入方式。
- 编辑器的真正价值在 v2 的多图与机关阶段，那时数据结构才稳定。现在写，等数据结构一变就要重写。
- 结论：**调试器是必须品，编辑器是负债**。

## 12. v2 扩展预想

### 12.1 现在已预留的字段

| 字段 | v1 状态 | 将来用途 |
|---|---|---|
| `StageDef.version` | 固定 2 | 数据迁移入口 |
| `Platform.id` | 数组下标 | 机关、破坏状态的稳定引用 |
| `shape: 'polyline'` | 只做校验 + 渲染 | 斜坡解算（需新增 `slopeMove()`） |
| `type: 'ceiling'` | 未使用 | 室内场地，压缩垂直机动 |
| `BgLayer.anim` | 已启用 | 天气、昼夜、灯塔闪烁节奏 |
| `World.stageId` | 常量 | 多图轮换、选图 UI |

### 12.2 v2 要加什么

- **场景机关**：`hazards: HazardDef[]`，每个机关有自己的确定性 `update(w)`，禁止读取外部时钟与随机源。
- **可破坏地形**：`Platform.hp` + 运行时 `BrokenPlatform[]`，碰撞查询改成「静态矩形 + 动态矩形」两段合并。这是碰撞层的大改，不要在 v1 塞半成品。
- **多张场地**：`data/stages/*.json` + 选图 UI。`World` 仍然只存 `stageId`，快照体积不变。
- **随机要素**：只能来自 `w.rngState`，且必须在 `step()` 内消费。加载期的随机（比如随机选图）属于元游戏，不进战斗快照。

### 12.3 什么不要提前做

- 不要给 `StageDef` 加 `hp` / `active` / `timer` —— 一旦有可变字段，它就不再是「只读、可哈希」的数据，回滚快照的引用语义会失效。
- 不要做平台编辑器（理由见 11.4）。
- 不要把复活平台塞进 `platforms`。运行时平台走 `World.respawnPlatforms[]`，与静态数据分离。
- 不要为了「将来可能的斜坡」去改扫掠算法。`maxStep=4` + 先水平后竖直的简单性，是 v1 最值钱的东西，保住它比支持斜坡更重要。
